# PXA 安装包压缩对比（2026-10-15）

本次是同内容压缩与开发机参考解码器的内存实验，尚未改变发行格式、Host 或商店策略，也没有 ESP32 解压速度和整机安装峰值结论。

## 当前格式

`.pxa` 是 PXA 自有签名容器，当前支持 store / LZ4，默认使用 `LZ4_compress_default`。
每个文件按 4096 字节独立压缩，压不小的块保存原文；每块有 4 字节长度记录。
Host 用 `LZ4_decompress_safe` 将块解压后写入安装目录，不在运行游戏时解压整个安装包。
安装器 workspace 包含 4096 字节输入及 4096 字节输出缓冲，另有结构体、manifest、签名和事务等开销，不能把 8 KiB 当作整个安装器内存。

## 同文件集体积

输入来自当前 ESP32-S3 浏览器 AOT 包和商店包，逐一验证 manifest 记录的文件长度与 SHA-256；没有更改代码、O3 或应用资源。
浏览器未压缩文件合计 885,055 B，商店为 734,207 B。
LZ4 估算结果与实际 `.pxa` 文件大小完全相等；其他 PXA 方案保留同样的签名/文件记录开销，按压缩数据 4 KiB 分段估算长度记录，尚不是可安装的新协议文件。

| 方案 | 浏览器 | 商店 |
| --- | ---: | ---: |
| 当前 LZ4 / 独立 4 KiB | 685,799 B / 669.7 KiB | 521,534 B / 509.3 KiB |
| LZ4 HC12 / 独立 4 KiB | 667,399 B / 651.8 KiB | 498,915 B / 487.2 KiB |
| Deflate9 / 独立 4 KiB | 570,954 B / 557.6 KiB | 411,850 B / 402.2 KiB |
| Zstd9 / 独立 4 KiB | 592,748 B / 578.9 KiB | 425,695 B / 415.7 KiB |
| Deflate9 / 每文件流式，32 KiB 历史 | 472,097 B / 461.0 KiB | 358,877 B / 350.5 KiB |
| Zstd9 / 每文件流式，32 KiB 窗口 | 487,343 B / 475.9 KiB | 366,191 B / 357.6 KiB |
| Zstd9 / 每文件流式，64 KiB 窗口 | 474,792 B / 463.7 KiB | 358,647 B / 350.2 KiB |
| Zstd19 / 每文件流式，64 KiB 窗口 | 435,862 B / 425.6 KiB | 328,481 B / 320.8 KiB |
| Zstd19 / 默认窗口 | 403,089 B / 393.6 KiB | 321,021 B / 313.5 KiB |

额外构建的普通 ZIP/Deflate9 包为 471,609 B 与 358,626 B，包含同样的包文件和包签名，但没有 PXA 容器外层签名，不能直接替代 `.pxa`。
ZIP 是容器，Deflate 是其常用压缩算法；可以在 PXA 自有容器内采用 Deflate，而无需引入 ZIP 路径、目录和签名模型。

这个实验同时包含压缩算法及历史复用方式差异。当前 4 KiB 独立块限制匹配范围，流式方案保留跨块历史，不能把全部收益归因于换算法。
相对当前包，流式 Deflate 在两份样本均减少约 31.2%；HC12 在无需更换解码格式的情况下分别减少 2.7% 和 4.3%。

## 参考解压内存

原生 C 程序对浏览器的 879,200 B AOT 文件逐次提供 4 KiB 输入和输出，用自定义分配器记录本次 decoder 分配峰值；流结束后计费归零。
下表加上两份 I/O 缓冲，不包含 libc FILE 缓冲、分配器实际元数据、调用栈、manifest、签名、文件系统及其他安装任务内存。
这是开发机 ABI 与参考库的实测，不是 ESP32 SRAM/PSRAM 峰值，也不是所有实现的理论下限。

| 方案 | decoder 堆峰值 | 加 8 KiB 输入/输出 |
| --- | ---: | ---: |
| 现有独立块 LZ4 | 无 decoder 堆状态 | 8 KiB，另有调用栈 |
| 流式 Deflate / zlib | 39,928 B | 48,120 B / 47.0 KiB |
| Zstd / 32 KiB 窗口 | 227,128 B | 235,320 B / 229.8 KiB |
| Zstd / 64 KiB 窗口 | 358,200 B | 366,392 B / 357.8 KiB |
| Zstd / 默认窗口，本样本 | 1,106,264 B | 1,114,456 B / 1.06 MiB |

Zstd 窗口上限不等于全部 decoder 内存；还包括上下文与流式内部缓冲。正式接入须同时设置窗口上限与分配总预算。
项目已有 PNG 的 miniz/tinfl，当前开发机 `sizeof(tinfl_decompressor)` 为 11,000 B；加 32 KiB 历史/输出环和 4 KiB 输入为 47,864 B，可作为复用现有代码的候选，但尚未完成安装器接入或真机速度测试。

## 建议与待验证事项

优先保留 PXA 的签名、manifest、原子安装和回滚模型，评估新增每文件流式 Deflate；安装时按需取得 workspace，完成后释放，不增加所有应用默认常驻内存。
LZ4 保留给低内存或调试安装；HC 可先改善构建端压缩，无需新固件解码器。
Zstd 小窗口作为 PSRAM 设备候选，其较小体积与更多临时内存是否值得，要根据实际下载、校验、解压及 Flash 写入耗时决定。不能用开发机吞吐量替代 ESP32 实测。

更换压缩不会减少安装后的 AOT、资源文件或运行时内存，也不直接提高游戏 FPS。更新期间的 Flash 需求仍包括上传包、新目录和旧目录；缩小上传包仅减少其中一项。进一步优化下载/落盘/验证流水线时仍须保证失败可恢复。

原始结果及脚本在工作区 `local/package-codec-20261015/`：`compare.py`、`results.json`、`memory.c`、`memory-results.json`。脚本记录压缩库版本；Python/ctypes 计时包含分配与往返校验，不作为纯算法速度测试。
