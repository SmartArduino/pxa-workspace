# GameKit 游戏 15fps 目标的设备验证记录

本轮最低目标为实际关卡 15fps，期望进一步接近 30fps。验收设备为 GameKit /
ESP32-S31、320MHz、16MiB PSRAM、320×240 显示。使用 RISC-V32 ILP32F AOT；
ESP32-S3 的 Xtensa 产物不能用于这台设备。桌面协议宿主的速度不作为真机 FPS。

## 已确认的设备结果

| 游戏与版本 | 场景、样本 | 结果 | 限制 |
| --- | --- | --- | --- |
| Duke3D SD 0.1.16 / FW21 | Hollywood Holocaust 屋顶，80～140秒59样本 | 中位15.9fps、最低14.8fps；30次转向采样均值16.09fps | 原320×240及音效/音乐开启；不能由此保证所有场景最低15fps |
| Duke3D SD 0.1.17 / FW22 | 同场景，4ms Clock | 中位14.9fps、均值15.35fps | 4ms 被正常接受，但没有性能收益，默认恢复8ms |
| Quake SD 0.1.2 / FW25 | START大厅80～140秒59样本；30次转向 | 中位5.9、均值5.75fps；转向中位6.9fps | 渲染约150ms/帧，尚未达到15fps；实际/最大线性内存3.4375/4MiB |
| Quake II SD 0.1.4 / FW25 | 冷启动签名安装后启动 | AOT读取完成，线性内存申请失败 | 申请10,878,976字节，8BIT总空闲10,908,779、最大连续块9,175,040；不能报告游戏FPS |
| Quake II SD 0.1.6 / FW26、27 | 冷启动，10.25MiB提前预留 | 连续预留成功，模块仍装载失败 | 借用临时重定位数组仍不足；尚无关卡或FPS结果 |
| C&C SD 0.1.6 / FW25 | 7MiB预留，持续加载360余秒 | 约4分钟后有菜单画面，菜单约53fps；随后任务加载窗口0fps | 菜单不计入关卡验收 |
| C&C SD 0.1.7 / FW25 | 第一个GDI试玩任务，约215～275秒55样本 | 中位34.9、均值33.86、最低7.9、最高42.5fps | 实际任务及触屏RMB通过；存在短时低帧，尚不能保证始终高于15fps |
| C&C SD 0.1.8 / FW25 | 同一试玩任务约179～239秒59样本 | 中位36.8、均值36.79、最低26.9、最高42.6fps | 该场景达到目标；热身30秒后采样60秒，窗口内不截图，默认音频开启 |
| Red Alert SD | 仅协议宿主试玩任务 | 待设备验证 | 不计入真机通过 |

原始设备记录保存在工作区忽略目录 `local/storage-device/`：
`duke-clock8-v016-first`、`duke-clock4-v017-valid`、
`quake-s31-byte-cache-v012`、`quake2-memory-probe-loopback`、
`cnc-s31-sd-only-v016`、`cnc-s31-canonical-v017`、`cnc-s31-handles-v018`。早期
`quake-s31-fastseek-v24-retry`的80～140秒窗口是菜单，已排除。
这些目录中的截图与日志用于复核，不包含在源代码提交中。

C&C 0.1.7在约2分钟后输出菜单，第一个任务约3分多钟进入，菜单与过渡画面不计入
稳定窗口。首个任务截图可见登陆艇、士兵及岸边场景。RMB按下/抬起记录在约255秒。
关卡FPS中的低值保留，没有把中位数当作每一秒的最低保证。后续需定位加载和资源
首次使用时的停顿，再重复完整采样。音频保持开启，连续性尚未单独量化。

0.1.8复用两个短期空闲的只读MIX句柄，保留READ_AT cookie与只读页，重开时
归零游标；500ms后由Clock回收，私有写入使覆盖判断失效，报错文件不复用。
相同协议宿主流程的控制请求进一步降至2,291次。WASM及ASan/UBSan测试通过。
设备第一次收到帧统计约105秒，前一版约127秒。此轮还将热身由10秒改为30秒，
并移走测量窗口中的截图；这些方法差异明确保留，不把低帧改善单独归因于缓存。
当前公开配置版本0.1.9采用同一策略，设备实测包为0.1.8。

## 已在设备验证的固件修改

运行线程的原生栈由12KiB扩大到32KiB，解决 Quake 在原生 AOT 调用链上的栈溢出。
这与 WAMR 操作数栈、Guest 链接器 C 栈及 Asyncify 续体缓冲相互独立。

启用 UART ISR 内部 RAM 执行后，2MiB 内部 Flash 文件以2Mbaud、1024字节分块
完整上传，SHA-256一致，没有重传。此前 Flash 缓存关闭期间会丢失上传命令。
启用 FAT 只读文件快速定位，每文件使用64个32位条目；`READ_AT` 的定位和恢复
不必重复遍历长簇链。未更改分区表或格式化存储。

FW25 增加 WAMR 映射申请失败的大小、空闲量及最大连续块日志，并拒绝尺寸加法
溢出。C&C 的诊断为申请8,388,608字节、总空闲10,129,507字节、最大连续块
8,388,608字节；实际映射还需要对齐头，不能把总空闲量当作可分配的连续空间。
原生映射保留增长、尾部清零、失败保持和尺寸边界的宿主测试通过。

FW25 对照镜像大小3,926,736字节，SHA-256：
`b0ff9637f5d2977287ae7ffd90d13793199cb18481663fa3b2745543df661756`。
镜像含工作区原有的未提交图像适配代码，相关功能提交不是整个镜像的完整可重现版本。

SDK 提交 `79fd546` 在装载 AOT 前预留固定线性内存，使用尚未启用的空间暂存节
数据和重定位数组。所有借用释放后，实例化精确匹配并接管、清零；失败或尺寸
不匹配会回收。未改动 Guest ABI、权限或上游校验。普通及 ASan/UBSan 的读取、
预留、引擎回归和映射测试通过，包含临时内容污染及相同额外堆限额的对照。

FW27 的 OpenLara 0.2.7 真机回归成功：8MiB 预留被接管，临时借用280,584字节，
应用启动及音频就绪，原有四个应用版本保留。Quake II 0.1.6 的10.25MiB预留成功，
但模块装载仍报分配失败，故未提前上传约50MB资源。总8BIT空闲包含内部RAM，
不能当作PSRAM容量；启动以来累计最低空闲也不能当作单次加载峰值。

## 本轮候选与后续验收

Quake 连续字节读取快路径补充独立8KiB不可变页，避免批量读取换页后悬空；
顺序读取、跨页、交错批量读取、越界及 NVM 回归通过 ASan/UBSan。
真机计时确认主要瓶颈在渲染，增大ROM缓存未改善本场景帧率。光照插值与完整
曲面缓存仍为私有试验；像素正确性与设备性能分别验证，不把宿主速度当作真机收益。

两种着色缓存均未采用：0.1.3光照插值缓存的真机稳定中位4.9fps，低于5.9fps
基线；0.1.4曲面缓存也约4.9fps，提前终止。试验源与产物留在忽略目录，生产代码
已撤回。后续候选缩小经水位测量的栈和续体，预留由4降至3.5MiB，并细分渲染
阶段计时；标准Wasm批量内存操作仍是待设备对照的独立试验。

Quake II 保留7.5MiB引擎池，缩小经水位测量的 C 栈与续体缓冲，冷模型加载器使用
尺寸优化。协议宿主在实际关卡和重新开局中为10.1875MiB，保留完整图像、音频及
原容量上限。离线网络层取消无套接字时的服务器休眠，恢复原上游的立即返回语义，
避免本地10Hz服务器限制客户端渲染。真机资格与帧率须单独验证。

C&C 缩小栈后在协议宿主进入实际任务，线性内存6.125MiB，栈水位为
引擎6968、回调424、续体660字节；7MiB预留已使真机装载成功。
更低引擎池导致 Quake II 资源加载失败的试验，以及出现间接调用签名错误的
Red Alert ThinLTO 试验均没有采用。

公共SD读取使用两页缓存合并小于512字节的只读请求，按打开句柄隔离，关闭即失效；
大块READ_AT及私有可变文件走原路径。WASM回归覆盖连续读取、跨页、独立句柄、
关闭后复用、EOF、失败恢复和大块旁路。C&C同一协议宿主任务的READ_AT由5,065次
降至964次；缺失资源不查询不存在的包内Assets，加上小写路径后，控制请求从约
10,400次降至5,006次。C&C/RA SD的设置与存档也统一ASCII小写；普通变体保留
原有解析。计时改用单调时钟。相关游戏仓库提交为`b33bc37`，设备任务FPS仍须单独验收。

Red Alert当前S31代码7,192,392字节，大于当前内部可用安装空间；即便只删除本轮
测试示例也不足。它尚未完成设备装载。不能把只读资源已在SD上的设计称为代码也
可在SD安装，或为绕过容量问题删除原有应用。

## 存储与上游

资源固定放在 SD `/PXA/media/<AppKey>/`，不要求用户选目录。代码与私有存档
目前仍在内部；整应用 SD 安装及无 Flash 文件分区启动尚未实现。
已验证的系统字体迁移见 [固定 SD 字体](../design/pxa-system-fonts.zh-CN.md)。

平台适配尽量位于 vendor 外；少量引擎钩子使用编译条件保留原行为。
`common/recrof/tools/upstream.py` 提供上游检查、三方合并准备、冲突处理和应用更新；
2026-10-19复核四个上游 HEAD 均未变化。工具不会自动提交或推送，也不会替代
合并后的设备回归。
