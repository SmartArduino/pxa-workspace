# GameRender 光照快速路径、双核调度与输入背压

在同一台 GameKit 上固定安装包集合，两端均冷启动，使用完全相同的测试包、
每场景三轮、每轮 100 个批次，水平光照跨度的 Host 执行耗时下降 **21.2%–40.4%**，
已有 fullbright 模式下降 **54.9%–61.9%**。输出校验值一致；原生差分检查逐字节比较通过。这是渲染
内核结果，不能换算成游戏 FPS。

Duke 0.1.35 在最终固件的实际 E1L1 关卡完成 60 秒显示计数和输入复测，LCD
完成帧率 **20.64 FPS**。本轮没有证明 Duke 整帧提速，也没有证明所有游戏达到 20 FPS。
这份 Duke 包使用原世界渲染器和 Host indexed 输出，不使用新光照跨度内核。

## 实现

- 光照插值在纹理行和光照格不变时复用垂直插值系数。针对两种纹理寻址、四种
  光照网格专门化；长度至少 8 且增量满足复用条件时进入快速路径，其他跨度
  保留逐像素实现。负坐标、10.6 坐标回绕、非二次幂纹理、插值精度不变。
- 已有 fullbright 标志单独选择内核，省去光照读取和插值，仍经过原 colormap
  第零行；没有为了提速而打开 fullbright 或改变游戏画质。
- 复用原生 raster worker。主核绘制自己的区域后可以原子接手另一核尚未开始
  的工作；另一核已经领取时，主核等待它完成。迟到通知不能重复执行，借用的
  Guest 内存始终在同步调用返回前使用完毕。indexed spans 和 triangle draw
  list 都使用这套机制。没有另起 Guest 线程执行上游的并行回调占位函数。
- 输入仅在 Core 接受之后从 Host mailbox 移除。相同连续手柄刷新用 16 字节
  状态缓存去重；按下、释放、连接变化、不同手柄及 UI generation/lifecycle
  变化仍需投递。pointer 的 peek/commit 保留 BUSY 重试，并用 epoch 防止清空
  后误删新事件。设备诊断确认旧实现把 `BUSY (-6)` 也记录成 delivered，并且
  可靠的重复手柄刷新塞满 Core 邮箱，触摸 DOWN/MOVE/UP 都未送达。

回调模式下，即使本次 pointer 投递遇到背压，事件分发释放空间后也要继续下一轮，
不能进入等待无关通知的休眠。最终检查补上了这个调度边界。

SDK 增加 Host C 查询 `pxa_ui_event_target_generation()`，让缓存随 UI 提交代次
失效。渲染包格式和 Guest ABI 不变，现有 GameRender 1.2 调用自动受益。
双核调度与内核作为一个固件候选测试，本次没有隔离出调度本身的性能增益。

## 内核实测

使用一次构建的 `pxa-render-kernel-probe` 0.1.0，基线和候选不重编应用。
最终对照固定安装包集合，两端刷写重启后等待至少 10 秒，不先运行游戏，直接
启动基准。候选为最终 `a8e892…` 固件，基线为 `833c845…`。开始时 SRAM
空闲均为 149,743 B，PSRAM 最大连续块均为 15,466,496 B。
每场景预热 10 批，测量 100 批，重复三轮。普通场景每批 61,440 像素；短跨度
场景每批 720 像素。表中为三轮 Host `execute_us / batches` 的中位数。

| 场景 | 基线 µs/批 | 候选 µs/批 | 耗时下降 |
| --- | ---: | ---: | ---: |
| 64×64，水平光照 | 7,658.00 | 6,038.22 | 21.15% |
| 64×64，斜向光照 | 7,037.47 | 6,960.21 | 1.10% |
| 64×64，fullbright | 6,666.60 | 2,537.66 | 61.93% |
| 64×64，3 像素短跨度 | 307.96 | 304.89 | 1.00% |
| 48×80，水平光照 | 8,341.57 | 4,974.30 | 40.37% |
| 48×80，斜向光照 | 6,180.32 | 5,919.21 | 4.22% |
| 48×80，fullbright | 5,846.03 | 2,637.20 | 54.89% |
| 48×80，3 像素短跨度 | 335.49 | 326.64 | 2.64% |

斜向和短跨度收益较小，不作明确加速结论。每轮批次、像素数、拒绝计数均核验，
各场景三轮及两份固件输出 FNV 校验值一致。校验值不能代替逐字节差分测试。
详细最小/最大值及含调用开销的 wall time 见
[冷启动对照](game-render-fast-20261021/render-cold-comparison.json)；原始带设备时间戳
日志保存在同目录的 `render-cold-baseline` 与 `render-cold-final`。

首次对照的水平光照耗时下降 21.6%–24.5%、fullbright 下降 54.8%–56.3%，
见 [初次记录](game-render-fast-20261021/render-comparison.json)，保留用于追溯。

最终固件在 Duke 测试之后再次运行 24 组基准，输出均与原基线一致，记录见
[追加复核](game-render-fast-20261021/render-final-comparison.json)。这次计时更低，
连未进入光照复用的斜向路径也出现明显变化；不能把运行状态差异归功于最后的
输入修正。它用于输出回归，性能结论采用上表固定安装集合、两端均冷启动的对照。

| --- | ---: | ---: |

pointer epoch 使用原结构的填充空间；4 字节 worker handoff 被链接段填充吸收。
光照复用仅有栈上系数，无纹理缓存、常驻副本或新堆分配。没有新增任务栈或帧缓冲。
这里是静态段差异，不是整条调用链栈峰值。

- 当前 vendor 原跨度函数：200,000 组比较、400,000 个跨度，覆盖负坐标、八种
  内核、分区及重叠写入顺序，逐字节输出一致。
- 原投影/光照/深度：40,000 组比较一致。
- 双核领取协议：100,000 个并发任务，检查恰好一次、载荷生命周期及迟到通知。
- 手柄：256 个 ID × 4,096 种按键状态，含连接、instance、generation、重试。
  pointer 包含 BUSY 重试、满队列、在途 MOVE 合并、追加边沿、reset 后同值事件。
- SDK UI、GameRender spans 与 ESP adapter host suite 在 ASan/UBSan 下通过。
  该主机测试使用当前 SDK 的既有改动；设备使用上述冻结源码，二者身份分别记录。
- 再从 SDK 提交 `275aacf` 单独导出 `libpxa`、`cmake` 和 `VERSION`，隔离未提交的
  GameRender 1.3 改动，重新构建并运行 UI、GameRender spans 的 ASan/UBSan
  检查，两者退出码均为 0。初次导出漏掉项目根的版本文件，补齐后重新配置。

可复现命令及退出状态见 [checks.json](game-render-fast-20261021/checks.json)。

## Duke 实际关卡与输入

最终 `a8e892…` 固件的 `duke-final` 复测通过：60,041,041 µs 内完成 1,239 帧，
**20.6359 FPS**；60 个瞬时样本均值 20.5583，范围 19.8–21.9，12 条新的关卡
记录。短按实际 ACK 间隔为 158,613 / 109,040 / 57,970 µs，均看到 Guest
按下/释放。上/下按视角投影移动约 +5,084.7 / -5,281.5，触摸/手柄悬浮按钮
切换和首次正常停止均通过。这是 60 秒平均值，不代表每一秒都稳定在 20 FPS 以上。
窗口内游戏日志的 Host 输出批次增量为 20.6310 次/秒，与 LCD 完成速率相符。

此前的渲染候选记录仍保留，用于追溯：

`duke-render-fast-verified` 的完整窗口为 60,041,901 µs，LCD 完成 1,215 帧，
**20.2359 FPS**；60 个瞬时样本均值 20.1683，范围 18.8–21.8。
12 条新的 `mode=4` 记录跨越 55,239 ms，窗口前后截图都是 E1L1 关卡。
显示明细环形缓冲溢出不影响独立的累计完成帧计数。

150/100/50 ms 请求均观察到 Guest 按下和释放；实际 ACK 间隔随报告保留，不能
把请求时长当成硬件时长。触摸恢复悬浮按钮，手柄按键隐藏，释放后保持隐藏，
断开后恢复。上/下各按 1 秒，按视角投影的位置变化分别约 +4,977.6 / -5,044.3，
验证了实际前进和后退。停止首次成功，没有旧邮箱阻塞导致的重试。

较早输入固件窗口为 21.1455 FPS，渲染候选另一个窗口约 20.48 FPS；两者控制
日志采集方式和完整性不相同，不能据此宣布优化提高了 Duke FPS。没有完成
同采样方式的反向复测，整帧差异的原因尚未隔离。

失败记录一并保留：修复前触摸确实未送达；`duke-input-fixed-run` 已通过短按
和前进，但后续位置日志等待超时；`duke-render-fast` 有完整 LCD 计数，但仅
收到 6 条关卡日志，未通过要求至少 8 条的验收。最终复测每 5 个样本补取保留
日志，仍按原设备时间戳过滤和去重，没有放宽完整窗口标准。

## 同步 Host 音频实机对照

两包固定在渲染候选 `4ac883…` 上测试，仅切换 `PXA_QUAKE_HOST_AUDIO_MIX`，
使用已记录 SHA-256 的 Audio 0.11 对照产物。通过签名目录安装，避免同时保留
压缩包和展开 AOT 的空间峰值；切换时只归档本任务的 Quake 程序，保留数据。
资源 `pak0.pak` 经设备 FSSHA 核验，23,778,536 B，SHA-256 为
`fbb30bad0cfbbbb71dcd2883ff00651d6ace9cf36fe390464fb44c8a2f9db176`。

两次完整窗口均进入实际关卡，HP=100，位置固定 `544,288,50`，每个窗口有
12 条新的关卡记录。两者都协商为 11025 Hz 双声道 S16LE 输入、48000 Hz
单声道设备输出；候选观察到 `Host S8 accumulation active`，基线没有该记录。

| 项目 | Guest 混音基线 | 同步 Host 混音候选 |
| --- | ---: | ---: |
| 60 秒 LCD 完成帧率 | 8.5947 FPS | 8.6780 FPS |
| 音频阶段记录中位数 | 1,858 µs/帧 | 2,152 µs/帧 |
| 视图渲染记录中位数 | 93,796 µs/帧 | 92,844 µs/帧 |
| 资源读取记录中位数 | 15,500 µs/帧 | 15,571 µs/帧 |

记录中的阶段存在嵌套，不能把各列相加；统计来自 5 秒区间的每帧均值，再对
区间取中位数。约 1% 的整帧差异不构成明确收益，音频阶段反而较慢，因此
**普通 Quake 构建保持默认关闭同步 Host 混音，设备恢复相同基线包**。
本次没有听音或捕获物理输出波形，不作听感/连续播放品质结论。已有离线混音
逐样本差分结果仍有效；本次也没有启用 reciprocal 重采样候选。

原始记录和静态/运行时内存见
[音频对照](game-render-fast-20261021/quake-audio-comparison.json)。

## 后续边界

Guest Quake 的材质准备、命令构建和世界渲染仍有独立开销；本次内核数据不能
证明换用整帧 Host 世界渲染就会更快。下一步应以同场景总帧时间分解确定迁移
哪些工作，保持资源生命周期明确、整批验证与工作量上限，并继续同设备对照。
小段混音逐声道跨 ABI 调用的开销值得继续检查，批量或资源句柄方案需要明确
源采样的有效期；本次没有增加异步声部或把 Guest 共享内存交给后台线程。
