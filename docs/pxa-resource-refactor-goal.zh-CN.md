# PXA 资源与 game-render 重构目标

这是供目标模式执行的任务描述与验收契约。具体设计见 [资源架构设计](pxa-resource-design.zh-CN.md)，实际落地状态见 [执行记录](pxa-resource-refactor-progress.zh-CN.md)。设计要求不代表对应能力已经完成。

## 用户修订：安装时校验，运行时信任已安装包

按用户最新要求，完整性/SHA 校验仅在安装阶段执行。运行时信任已安装包，不防范安装后文件被修改；移除资源加载、索引加载、音乐/地图流读取的重复 SHA、块摘要表、专用校验缓冲及其额外拷贝。仍保留路径归属、格式/尺寸/长度、越界、预算、I/O 错误和生命周期检查。此修订覆盖本文和设计文档此前要求的“消费前块认证”与“安装后篡改检测”；这些不再是验收目标。共享存储竞争、音频恢复、内存和性能验收继续执行，安装器的签名及内容校验保留。

## 可直接提交的目标描述

在当前 pxa-projects 工作区完成 PXA 图片、纹理和音频资源管理重构，让大型资源独立于 AOT，由 Host 按需加载和管理，降低内部 RAM、PSRAM、Guest 线性内存的峰值与稳态占用，同时保证游戏渲染与音频播放不被资源 I/O 阻塞。

允许修改包格式、ABI、Guest SDK、Host、game-render、模拟器、ESP 后端和示例应用，允许破坏旧兼容。以更简单的所有权、更少的资源副本、有界内存和可测量的性能为优先，不为兼容保留两套长期并行实现。保留当前工作区已经完成的有效改动，不覆盖与本任务无关的修改。

使用主机测试、桌面模拟器、可注入延迟和内存限制的测试后端验证，并完成 Pai Touch 与 Sensecap Watcher 的固件构建。2026-09-28 用户补充了实机条件：Pai Touch `/dev/ttyACM0`，ESP32-S31 Korvo-1 `/dev/ttyUSB0`、2000000 baud；增加这两块设备的实测和 S31 固件构建，保留原有模拟验收及 Sensecap 构建要求。模拟器结果不能当作 ESP 的实际 FPS、带宽、功耗或延迟。自行决定常规技术细节，持续完成实现、迁移、测试和文档，不因阶段性完成而停止，也不询问常规实现选择。

按本文后续架构、范围和验收要求执行。开始前记录当前工作区基线；完成时交付代码、迁移示例、可复现测试和前后对比报告，而不是只交付设计。

已有阶段实现与基线时先核对并复用，不重置进度、不覆盖原始对比数据。以实际源码和可重跑测试判断完成度；“接口已声明”“局部测试通过”和“完整目标通过”分别记录。具体模块改造与 SDK 取舍见设计文档第 8 节。

## 一、架构约束

### 1. 资源独立于代码

- 大型图片、纹理、音乐和音效放入包内资源区，建立包含类型、格式版本、尺寸、编码、存储大小、展开大小和完整性信息的资源索引；复用已有清单和签名体系，避免重复设计信任机制。
- Host 验证路径、偏移、长度、尺寸和展开上限。资源访问限定于调用应用的包；不能通过路径穿越、软链接或句柄复用读取其他应用的数据。
- 包内资源只读访问与应用私有可写 FS 分开。用于纹理和音频的文件不必先复制进 Guest 内存。确需由 Guest 解析的地图等数据，提供有界分块读取入口。
- Guest 数据读取必须定义短读、EOF、越界、取消和事件数据的借用期限；使用现有请求 token 与事件分发，不保存 Guest 原生指针。验收单次请求上限、事件容量不足时的立即拒绝，以及已接受请求恰好一次终态；同时核算读取缓冲、完成事件和 Guest 接收区的重叠占用。
- 构建时把原始图片转换为渲染器可以直接使用的版本化纹理格式，优先使用当前 INDEX8 与 RGB565 调色板能力。无需为了本任务引入新的通用图片编解码器。
- 优先支持逐资源独立读取；需要压缩时使用独立资源或独立块压缩，禁止为了使用一张纹理而展开整个资源包。
- 不机械地把所有常量和程序纹理改成文件。小常量可以保留；对 voxel-craft 的程序生成纹理比较生成代码、生成缓存和离线资源的实际成本，再选择更省内存的方案。

### 2. Host 管理资源，Guest 使用句柄

- 提供包内资源发现/查询、异步纹理加载、预取、状态查询、取消和释放；简单场景应能通过一条 SDK 调用加载纹理，不要求用户手写协议或管理解码缓冲。
- 复用 PXA 现有完整宽度、带代际校验的句柄机制，并检查应用/组件所有权。Guest 不持有 Host 指针，也不直接映射原生内部 RAM。
- 分清请求 token、资源句柄、渲染绑定和缓存条目。异步请求具有明确的成功、失败、取消和完成语义；重复请求可合并，失败不会发布半成品资源。
- 服务版本、包能力、SDK 常量与两平台注册表使用共同定义或一致性测试，避免协议已经更新而实际包激活仍拒绝新版本。
- 共享已准备好的不可变资源；去重键包含包身份、版本或内容身份，以及转换参数。不同应用的授权和生命周期仍需独立。
- 同一格式、同一版本的纹理在 UI 与 game-render 间能够复用时才共享表示；无法直接共享时显式计入转换副本，不以“统一接口”掩盖额外内存。
- 保留动态和程序生成纹理入口。这是有效使用场景，不能因为改成文件资源而删除。

### 3. 渲染过程不依赖文件读取

- 资源加载、解码和准备运行在有界 Host 工作队列中，不在 Guest 帧回调、渲染线程、音频实时回调或关中断的临界区中执行。
- 稳态绘制与混音路径不进行文件 I/O、解码、资源装载或堆分配；也不等待加载任务持有的长时间锁。
- DrawList 使用已就绪资源的引用。句柄验证和解析在提交/准备阶段完成，像素循环只访问已经解析的纹理视图，不能逐像素查询句柄表或加锁。
- 移除“第一帧后不能上传/更新纹理”的限制。资源绑定在明确的提交边界生效；同一帧看到一致的绑定快照，不会在执行中途读到替换后的纹理。
- 提交中的、排队中的和正在执行的帧持有必要的资源引用。资源替换、取消、掉帧、上下文关闭和应用退出都必须正确释放引用；最后一个消费者完成后才回收内存。
- 根据消费者实际完成时机释放：CPU 光栅化完成后不必仅因画面仍在显示而保留源纹理；被 DMA 或零拷贝显示直接引用的资源则必须等相应完成信号。
- 预加载场景必需资源，再进入正常渲染；后台预取下一批资源。加载未完成时明确使用占位图、延迟显示或加载画面，禁止绘制时同步补读文件。

### 4. 内存必须有上限

- 配置内部 RAM 热资源预算、PSRAM 驻留预算、解码临时空间上限、并发加载数和请求队列长度，并区分全局预算与应用额度。
- 文件资源、动态上传、UI 转换和音效缓存不能绕过总预算。索引、缓存元数据、任务栈、解码器、文件 I/O 状态、帧缓冲与渲染 scratch 单独记账，再汇总到完整内存报告；不得将纹理载荷预算宣称为整个子系统的内存上限。
- Host 统一管理加载任务数量，优先复用已有音频任务，不随应用、资源句柄或请求数量新增线程。跨应用共享资源不是前置条件；首先保证应用隔离、全局限额和同应用去重。
- 加载前预留容量；解码、排队、临时副本、新旧场景重叠和未完成帧引用的资源都要计入预算。不能只限制最终缓存而忽略加载峰值。
- 内部 RAM 优先保留给 DMA、音频实时数据、调色板和经验证有收益的小型热纹理。不得让纹理缓存无上限地消耗内部 RAM；也不要未经测量就每帧在 RAM 层级间搬运纹理。
- 只淘汰没有有效持有者和在途消费者的缓存条目。场景驻留与预取引用应可显式释放，避免长期 pin 住所有资源导致缓存无法淘汰。
- 内存不足返回明确的资源限制或背压状态，不能忙等、偷偷丢失已接受的数据或越过预算。新旧场景无法同时驻留时，允许先切到低资源加载画面，再回收旧场景；不能永久等待自己持有的资源释放。
- 短期 Guest 缓冲释放不等于 Wasm 线性内存缩小。消除不必要的 Guest 资源副本与高水位增长；不要把 malloc/free 后的逻辑空闲误报成 PSRAM 已归还。
- 不把 AOT 按需分页、Flash XIP 或修改整个 WAMR 加载器作为前提。先移出大资源，减少模块数据与线性内存中的重复；保留底层加载器仍需要的 AOT 缓冲，不能提前释放。

### 5. 音频复用现有成果

- 保留已实现的三会话 PCM/合成音混音、EQ、Ogg Vorbis/Opus 流式解码、短音效缓存与暂停/恢复行为；统一资源索引、权限、配额和取消机制，不重写一套并行音频框架。
- 短音效提供显式预加载；冷加载在工作队列中完成，不能在实时回调里读文件。保留缓存命中时的低延迟播放路径。
- 音乐维持有界流式缓冲，不随文件时长分配整首 PCM。音频补充数据不能被大型纹理加载长期饿死；使用分块 I/O、受限并发及可说明的调度优先级。
- 区分预算上限与播放准入保证；按输出消耗速率和可覆盖供给停顿确定缓冲，并验证预取压力下的工作区可用性。超出供给能力时报告欠载并恢复，不无限扩容，也不以平均带宽替代竞争测试。
- 补齐文件播放的完成和错误通知，区分“命令接受”“资源就绪”“播放结束”。高频 PCM 和 DrawList 仍使用直接 I/O/有界队列，不能为每个采样或像素生成事件。
- 一次播放具有独立于会话的身份，换曲后的旧通知不会影响新播放；关闭音效资源句柄不截断已接受的播放，停止操作与资源释放语义分开。
- 播放准入具有事务性：同步拒绝新播放时保留旧播放及其控制状态；接受后才允许替换。明确 READY 是可供输出的缓冲已准备，ENDED 是该实例最后一段输出已完成，不能用解码器 EOF 代替。停止、替换和失败分别报告一次终态。
- 通知容量必须有界。Core 事件池满时保留已接受播放的待投递状态，在运行时线程重试；不能在音频回调中阻塞投递，也不能用丢弃终态换取无限接受新播放。容量耗尽立即背压，实例关闭后按生命周期规则清理。
- 应用后台、锁屏、恢复和退出时正确暂停/取消工作、释放引用，防止旧应用的异步完成影响新实例。

## 二、实施顺序与交付物

1. **记录基线。** 固定版本、编译模式、分辨率、画质、工作负载和输出结果，分别记录 AOT 大小、Guest 线性内存高水位、资源副本、Host 分配字节、内部 RAM/PSRAM 用量及分配失败、缓存峰值、加载延迟、渲染时间、音频欠载与队列状态。主机没有真实 PSRAM 时记录按 ESP 内存类别标注的分配，不能只拿进程 RSS 代替。
2. **定义协议与所有权。** 写清资源格式、句柄、状态转换、取消规则、内存预算、帧引用和错误语义。需要破坏 ABI 时明确升版并拒绝无法解释的旧包，不能静默误读。
3. **完成最小端到端路径。** 包内纹理 → Host 异步准备 → Guest 收到句柄 → game-render 绘制 → 释放。再接入预取、预算、替换、UI/音频复用，避免一开始建立过大的通用框架。
4. **迁移真实应用。** 迁移 voxel-craft 中适合迁移的资源路径；再选择一个图片/精灵资源较多的现有应用。若没有合适应用，补一个小型场景切换样例。加入纹理加载、换场景、短音效预加载和背景音乐同时工作的示例。
5. **压测与收尾。** 完成异常、生命周期、预算和长期切换测试，构建两个模拟器入口及两个 ESP 板配置，更新 SDK 文档、打包说明和前后对比报告。两个 ESP 构建共享 managed_components，必须顺序执行。

## 三、完成标准

以下项目全部满足后才能声明目标完成：

- 包工具、Host、Guest SDK、game-render、模拟器和 ESP 后端真正打通。不能只增加接口、返回伪成功，或只让模拟器支持。
- 迁移后的文件纹理不会作为大型像素数组同时驻留 AOT 与 Guest 线性内存；绘制期间无需重新读取文件或上传纹理。
- 具备可复现资源基准：至少准备 20 张 256×256 INDEX8 纹理，每个场景只固定使用其中 4 张。使用显式缓存预算，例如 512 KiB 驻留预算加独立且有上限的工作空间，连续切换至少 100 次；预算与背压行为符合契约、内存不随切换次数增长、输出正确。测试中的预算不是所有板子的强制生产默认值。
- 能在旧帧仍在执行时替换资源并立即释放 Guest 句柄；旧帧、新帧都正确，没有 use-after-free、越权、重复释放或旧句柄误命中新资源。覆盖排队帧被丢弃和应用中途退出的情况。
- 覆盖缺失/格式错误的文件、非法路径、超大声明尺寸、展开超限、加载中取消、重复加载、队列满、内存不足、冷缓存、热缓存和慢存储。低预算必须可恢复，不能靠无限扩大缓存通过测试。
- 能在纹理加载/换场景的同时持续播放音乐和触发音效。使用可重复的 I/O 延迟注入验证非阻塞行为；在设定供给足以维持播放的测试条件下没有新增音频欠载，供给不足时能够诊断和恢复。
- 上述音频竞争测试必须覆盖音乐和资源读取共同经过的存储限制，记录带宽、单次阻塞、突发停顿、读块大小及解码时间；只延迟纹理 worker 而让音乐绕过限制不能算作共享存储竞争验收。流式内容信任安装阶段的校验结果，不进行运行时 SHA；测量对应启动延迟、读取缓冲和索引成本。
- 同分辨率、同画质、同绘制量、同可见结果下，至少一个真实应用或有代表性的资源基准出现可测量的资源相关峰值与稳态内存下降。分别报告数据段、Guest 高水位、纹理驻留和临时缓冲的变化，不能通过减少可见内容或降低画质制造收益。
- 热缓存下绘制结果与基线一致，不能因引入资源管理增加逐像素查找、锁或每帧加载。固定工作负载多轮测量 CPU 渲染时间和帧时间 p50/p95；超过基线约 5% 的可重复回退必须定位并修复，不能用平均 FPS 或 VSync 封顶掩盖回退。记录测量噪声、构建参数和原始结果，不宣称模拟器结果等同 ESP 实测。
- 生命周期回收、主机回归、相关 sanitizer 检查、实际模拟器运行，以及 Pai Touch / Sensecap Watcher 固件构建通过。保留可一键重跑的相关测试。
- Guest SDK 提供无需手写报文的异步加载、明确的结果解析、资源释放和批量绑定用法；完整示例覆盖加载画面、进入场景、预取、换场景及退出。低层 ABI 与易用封装共用实现，不能各自建立请求调度器或隐式常驻缓存。
- 交付最终架构与 API 文档、迁移示例、测试命令、内存/性能对比、保留限制和真机待测项。SDK 示例标明真正可用的 API，不把设计伪代码冒充已实现接口。

### 对比报告的最低要求

每项结论附基线与最终版本身份、构建参数、运行命令和原始结果。当前工作区包含未提交改动，基线应保存相关源码/产物摘要，不能只用 Git HEAD 代表实际测试版本。

| 维度 | 必须报告 |
| --- | --- |
| 代码和 Guest | AOT、数据段、线性内存高水位；区分文件大小、逻辑分配与实际驻留 |
| Host 内存 | 内部 RAM / PSRAM 的同时存活峰值及稳态；列出资源、索引、事件、栈、解码器、帧缓冲、scratch 与未覆盖项 |
| 加载 | 冷/热加载延迟、读入字节、格式检查与转换成本、缓存命中和失败/重试次数 |
| 渲染 | 同输出下多轮 CPU 渲染与帧时间 p50/p95，附像素或图像一致性检查 |
| 音频 | 并发加载时欠载计数、缓冲高水位、取消和恢复结果，以及注入的 I/O 延迟 |
| 退出 | 应用相关预算、请求、句柄和在途引用回收；设备常驻对象单独列出 |

总峰值应使用同一时间轴的观测；不能简单相加各项在不同时刻出现的峰值并称为实测总峰值。无法观测的底层内存明确标为未覆盖，不用零代替。先测量再决定性能优化；不提前承诺未经验证的固定节省百分比或 ESP FPS。

## 四、本轮不强制包含

不要求新增 MP3/WAV 编码支持、GPU 渲染后端、通用虚拟内存分页、纹理压缩硬件扩展、完整引擎编辑器或全面重写 WAMR。也不要求将所有 UI 图片和游戏纹理强行变成相同像素格式。只有明确阻碍上述目标时才扩大范围，并在报告中说明理由与验证结果。
