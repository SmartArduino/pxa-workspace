# 游戏音效混合与合成迁移到 Host

状态：接口设计稿，尚未发布新的 ABI。当前游戏仍在 Guest 中执行原引擎的音效混合和 OPL/FM 合成。本轮先优化现有 Audio PCM 通路；不能把它描述为原引擎混音已经迁移完成。

## 分工

Guest 保留游戏规则、声源空间定位、遮挡、声部选择和音乐事件调度。Host 接受有界的播放指令，持有音频资源，负责采样插值、声部混合、合成和设备输出。音频归属 Audio 服务；不放进 GameRender，不依赖显示刷新和帧率。

当前路径：

```text
Guest 原引擎：音效/音乐 → 混合 → PCM
  → Audio 0.10：复制源采样率 PCM
  → Host 音频任务：重采样 → 增益/EQ/系统混音 → I2S
```

目标路径：

```text
Guest：游戏状态 → 声部指令 / 带时间戳的合成器事件
  → Host：持有采样资源 + 原合成器状态 → 混合 → 设备输出
```

PCM 流仍用于视频、串流和没有完成迁移的引擎。新路径复用音频输出任务及系统音量、暂停和预算机制，不另建一个游戏音频设备。

线程、核心和优先级由 Host 按板级负载决定，不进入 Guest 音频 ABI。音频任务独立于游戏帧更新，并不意味着必须固定到另一核；LCD、光栅和音频可能争用同一核或内存带宽，调度策略必须通过真机对照确定。

## API 和资源所有权

下表是待实现的操作语义，不是当前可调用的 SDK 函数。

| 操作 | 语义 |
| --- | --- |
| 查询能力 | 支持的采样编码、采样率、最大声部数、命令容量、资源预算和合成器类型 |
| 准备采样 | 从 Host 资源句柄的有界区域读取，或复制 Guest 提供的采样；异步返回不可变采样句柄 |
| 提交声部批次 | 一次提交 start、stop、gain、pitch、position 等控制，所有指令先验证，再整体入队 |
| 查询播放时钟 | 返回会话音频帧时钟和声部游标，区分已消费和物理 DAC 已播放 |
| 创建合成器 | 按能力创建明确的合成器类型和版本，不把通用波形 API 当作 OPL 替代品 |
| 提交合成事件 | 按音频时间戳提交寄存器写入或 MIDI 事件；音色资源同样由 Host 持有 |

采样描述包含编码、单/双声道、源采样率、帧数和 `[loop_begin, loop_end)` 循环区间。首批编码考虑 S8、U8、S16LE；采样字节序、声道交错方式、范围验证写入协议。声部描述包含采样句柄、起始帧、播放速度、左右线性增益、循环模式和生效时间。SDK 对外使用类型明确的参数，wire 不传 C 结构体布局或原始指针。

游戏档案中的声音可以从已经授权的资源区域准备，不要求把 PAK/GRP 拆成成千上万个文件。资源 worker 完成读取/解码，音频线程只读取已就绪的不可变 PCM。不能接受 Guest 的任意文件路径、裸地址或无限制档案偏移。

资源入口优先复用 Core 句柄和 Assets 已有的 FILE/STREAM 源资源机制：准备操作明确输入长度和 PCM 描述，异步返回 AUDIO 资源句柄。这样 flash、SD 卡及其他已挂载设备由文件系统统一处理，Audio 不再实现一套挂载点解析或私有路径缓存。音频元数据使用独立的采样描述，不借用图像的 width/height 字段。读取期间源句柄的独占、取消、字节上限和晚到完成沿用已有资源规则。

Guest 临时上传的采样在返回成功前完成复制；批次中的句柄在发布前取得引用。后台线程不会持有 Wasm 线性内存的裸指针。大数据进入受现有资源预算约束的 PSRAM 缓存，热状态和命令有固定上限；关闭 Guest 句柄不会提前释放仍在播放的资源。

## 时间、队列与退出

时间基准是会话音频帧时钟。每个批次带一个基准时间和相对帧偏移，避免每个采样一次 ABI 调用。入队成功表示接受，不能混同于 DAC 播放完成。队列满时返回 `WOULD_BLOCK` 且保持原状态；失效句柄、越界循环和不支持的参数使整批失败。

音频任务按小块消费批次，块内按事件时间分段。迟到命令按明确策略在下一可执行采样点生效，并累计迟到数量；不能静默重排 start/stop。音量等连续控制可在尚未消费的同一逻辑更新内合并，但不可跨越播放、停止、跳转事件。

声部句柄包含代次，旧声音的结束事件不会修改复用后的声部。暂停冻结会话的音频时钟、游标和合成器状态；恢复不补播锁屏期间的积压事件。关闭会话先禁止新提交，音频消费者确认停止引用，再交由非实时路径回收资源。不得在音频锁内等待 Guest、读 SD、分配内存或回调游戏。

## 保持原引擎声音

通用的高质量线性混音不自动等于原引擎输出。迁移前必须记录每个引擎的输入格式、增益量化、插值、累加位宽、削波、最终量化和循环规则。

Quake 当前 ESP 移植路径在 `snd_dma.c:S_Update_` 按播放游标重算环形缓冲，`snd_mix.c:SND_PaintChannelFrom8` 将 S8 采样乘以量化到 8 的倍数的左右音量，累加后经过主音量、S16 饱和和 U8 输出量化。直接换成 Host 的 16 kHz 预加载短音效会改变这些行为。第一款迁移应先以固定声音指令录制为输入，逐采样对比原实现，再用音频时钟替换其环形缓冲假设。

Duke3D 的多声部采样混合和 OPL 音乐是两个迁移单元。OPL 应提取原合成器或选定经验证的同等实现，锁定版本、许可、寄存器时序和输出采样率；不把 FM 音乐换成简化的 sine/square 音色。C&C 等游戏的流式音频解码另走已有 worker，音频实时线程不解压档案。

是否需要显式的兼容混音模式，由逐采样差异决定。不要先在公开 ABI 中固化游戏名或指向引擎内部结构的接口。

## 实施和验收

1. 先完成现有 PCM 通路的消费者重采样和单 PCM 快速路径；保持采样输出、包边界、背压和内存容量不变。增加已有音频任务的板级核心配置，分别验证与 Guest 同核、异核的实际表现后选择默认值。
2. 实现受预算约束的采样句柄和声部批次，先接一款游戏。Guest 适配通过 port 层和可重放的上游补丁完成，不直接堆积无法同步的 vendor 修改。
3. 独立迁移 OPL/FM，测量合成峰值、实时截止时间和堆栈，再决定声部与合成器上限。不能先承诺所有设备都能同时支持固定数量的声部。
4. 记录同一固件配置、同一 AOT 包、同一场景下的 FPS、提交耗时、音频块耗时、队列低水位/欠载、SRAM 与 PSRAM 峰值。渲染已占据两核时，新增音频并行仍要考虑争用。

正确性覆盖：不同块大小输出一致、循环边界、音高变化、左右增益、削波、命令批次原子性、资源关闭后播放、队列满、暂停/恢复、快速重启和停止时资源回收。硬件运行验证与主机逐采样测试分别记录；没有音频采集或实际听音证据时，不声称听感、无爆音或 DAC 连续性已经验证。

音频优化的直接目标是减少游戏线程工作量和保持播放稳定。Quake 当前渲染耗时远大于声音处理，完整迁移音频也不能单独保证 20 FPS。
