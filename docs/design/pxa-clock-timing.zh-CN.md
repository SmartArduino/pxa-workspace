# Clock 周期与调度能力设计

状态：设计提案；当前可用接口仍为 Clock 0.2。

当前 `set-period` 的线格式是毫秒 `u16`，0 取消，16～1000 有效。这个范围由规范、C/C++ SDK 和 Host 同时检查，是协议政策，不是 ESP32 的硬件计时下限。GameKit Host 当前每 5000µs 扫描到期定时器，事件可合并；8ms 请求即使只放开参数检查，也不会成为精确的 8ms 回调。

## 后续接口

保留现有操作的语义，为支持更高频率或更长周期的 Host 增加显式能力和新操作。旧应用继续工作；新应用须声明相应服务版本/能力，不把旧 Host 当成支持新范围。

- `limits`：一次查询返回 `min_period_us:u32`、`max_period_us:u32`、`period_step_us:u32`、`dispatch_quantum_us:u32` 和能力标志。周期必须位于范围内，且为步长的整数倍。`dispatch_quantum_us` 描述计时调度的量化尺度，不承诺最大回调延迟；Guest 忙碌、系统负载和暂停均可推迟投递。
- `configure`：使用有请求 token 的完成消息，参数为微秒 `u32`，0 取消。成功返回实际配置周期；不支持的数值明确报错，不静默修改成另一个周期。应用需要近似值时，先根据能力自行选择，再提交配置。
- 各设备报告真实范围。8ms、33ms、100ms 都只是范围内的普通参数；不要求所有设备接受任意数值，也不要求每个应用都申请最高频率。
- 延迟后只保留一个待处理 tick，携带最新单调时间。不得补发一串过期 tick；游戏按真实时间推进并限制追赶步数。后台暂停、组件销毁及权限/生命周期边界沿用现有资源回收规则。

## Host 实现原则

采用到最近期限的一次性定时器，重新配置、取消、恢复和事件消费后重新计算最近期限；没有活动定时器时停止硬件唤醒。定时器线程只登记/投递事件，不执行 Guest；每个组件最多保留一个待处理 tick，避免高频请求挤满事件队列。跨线程重新安排必须序列化，并利用 generation 丢弃取消前的旧事件。

周期表示请求的唤醒节奏，不是帧率或硬实时保证。30fps 的帧预算约 33.3ms，16ms 唤醒可以满足其调度需求；最终帧率仍由引擎计算、资源读取、让出等待、显示提交和设备负载共同决定。

## 实现验收

新能力发布前须完成 SDK 与 Host 范围一致性检查，以及最小值、8ms、33ms、长周期、取消、重配置、溢出、后台恢复、组件销毁、事件合并和旧 Host 拒绝的回归。设备上分别记录空闲唤醒、投递间隔和负载下抖动；不能用协议宿主的 tick 数证明设备精度。目前没有发布该扩展，现有游戏继续使用已支持的 16ms。
