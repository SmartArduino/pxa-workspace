# 游戏常驻调用栈与音频格式重构草案

状态：**待实现**。现有固件仍为 Core 2 回调模型，所有可执行游戏包仍使用 Asyncify。
本文件不发布新 ABI 编号，不将离线代码体积对照视作可运行移植。
动机与产物摘要见 [2026-10-20 真机及体积记录](../validation/game-render-followup-20261020/README.md)。

## 需要解决的成本

GameRender 1.2 已经能合并世界材质并借用 Guest 缓冲，但 Quake 整帧仍未达标。
仅优化输出转换对 Duke3D 的平均 FPS 提升约 1%，不应继续把小批次封送当作主要方向。
RA 使用相同 C/C++ 对象、相同 Binaryen 优化和标准 WAMR 参数时，去掉 Asyncify
可使 TEXT 从 6175548 降至 3159212 字节。该诊断表明执行模型值得重构，
尚不能证明实际主循环改造后会节省同样字节或达到某个 FPS。

音频也有独立缺口：当前链路固定 16kHz 单声道，低于 C&C 上游的默认源格式。
性能验收必须同时记录源格式、协商格式、实际设备格式和连续性，不能静音换帧率。

## 常驻调用栈的最小闭环

增加可协商的游戏主循环执行模式，首次激活完成后在既有运行线程进入 Guest 主循环。
游戏通过阻塞的事件等待点让 Host 处理控制和 I/O，C/C++ 调用栈保持在原线程上。
游戏循环最终返回时才退出该次 WAMR 调用，不再为每次文件/Clock 回应展开和重放栈。
原回调应用继续走当前调度路径。

首版只支持一个前台游戏 Guest。包校验拒绝将多个常驻 Guest 或后台 Job 与该模式
组合，避免暗中失去公平性。正常的 Host 音频、显示和 I/O worker 不受此约束。
不新增 WASM 线程，也不增加第二个 32KiB SRAM 运行栈。

### Core 与 SDK 边界

保留 `pxa_call`、`pxa_io` 两个进口。拟通过 Core 控制请求取得仅限本 Component
的事件端口句柄，使用其 `WAIT` I/O 操作接收一个标准事件信封。
具体 opcode、资源类型和版本号在 schema、协商及测试一同实现时分配；
现有的 0 句柄不会被无版本地重新解释。

- 请求含明确的小端超时/容量字段；响应只包含实际事件字节数与标准信封。
  SDK 接受调用者缓冲，解码视图只在下一次覆盖前有效，不分配 Host-to-Guest 对象。
- `timeout=0` 是非阻塞探测，有限超时返回可区分的无事件状态；停止/撤销返回取消状态。
  时间、长度及加法必须检查溢出，超时上限由 Host 协商。
- 队首事件大于容量时保留队列与目标内存，返回明确的所需大小/资源限制，禁止截断。
- 内部沿用现有权限、待决 token、取消和事件顺序。先取就绪事件，再决定是否睡眠；
  注册唤醒和再次查队列必须避免完成通知与休眠之间丢失唤醒。
- 每次调用重新验证当前线性内存与句柄所有权。等待期间不允许其他路径进入该 Guest，
  返回后不保留 Guest 指针，不要求为普通应用新增固定线性内存预留。

SDK 的同步 `port_rpc` 变为“提交请求、等待匹配 token、处理期间收到的输入/生命周期”。
期间处理事件是 Guest 内部普通 C 调用，不能递归调用 WAMR 的事件出口。
文件桥接、保存、音频和渲染继续使用统一服务，不新增游戏专属文件系统。

### Host 所有权与取消

复用当前 Runtime 线程的服务轮询与命令处理，抽出一个不进入 Guest 的有界维护步骤。
事件等待点可以调用该步骤，处理 Clock、FS 完成、输入、音频通知和取消，
然后从现有事件队列复制事件。`engine->busy` 始终保持，不绕开现有重入保护。

卸载、替换包、切换运行时、释放线性内存等命令不能在常驻调用内部执行。
先标记停止/唤醒等待，必要时请求 WAMR 终止，等外层调用退出后再统一撤销和销毁。
取消与 I/O 完成竞争时只能有一个终态；等待者退出后，旧实例完成通知不得投递到新实例。

看门狗仍检查 Guest 连续执行的时间。只排除 Host 明确处于等待/维护中的时间，
在退出等待前恢复下一段执行期限；绝不因“主循环模式”关闭超时处理。
睡眠计时与执行计时分开记录，不将主动让步等价于帧完成。
系统锁屏、切后台和 HOME 必须能在一个合作期限内生效；返回前台时先释放旧输入状态。

### 必须一起交付的验证

先用极小 Guest 验证启动、同步请求、输入、超时、HOME、正常停止和强制终止，
以及事件不足容量、memory.grow 后重取基址、取消竞争、旧实例通知、无嵌套 Guest。
然后只迁移一个私有 RA 构建，完成签名安装、装载、实际关卡和内存采样。
与旧回调游戏交替运行，验证不用新增线程/栈并正确回收端口。
通过这些检查后，才在 Quake、Quake II、Duke 中做同场景 60 秒对照。

## 音频格式与有界队列

将源 PCM 格式与设备输出格式分开协商。保留旧的 16kHz 单声道客户端；
新客户端请求源采样率、声道数和有界队列时长，Host 明确接受或返回不支持。
不默默将 22050Hz 的请求当作 16000Hz 成功。

首个目标是恢复 C&C 原混音采样率和立体声来源，移除公共 U8 桥接的提前下混。
在公共音频边界保留源声道，直到板级设备确需下混；GameKit 的单扬声器能力在
能力查询与测试记录中明确显示。支持更高率的板级 I2S 输出后再谈保真通过，
不能只在应用端改常量或将 16kHz 流上采样后宣称恢复原质量。

缓冲按时间预算在 PSRAM 中一次分配，包的大小由格式推导，SRAM 只保存队列索引
和必要 DMA 存储。格式切换只在关闭/清空会话后发生。Guest 提交同步复制或明确
借用到返回为止，不让音频 worker 持有可增长线性内存的原生指针。
重采样器保留跨包相位；队满、丢弃、静音补齐和实际 sink 接受帧数分别计数。

验收应包含 11025/16000/22050Hz 源、单/双声道、分包边界、环绕、负数奇数下混、
重采样累计帧数、静音、削波、暂停/恢复、队满和长时连续输出。
真机测量保留相同音量、音效与音乐开关，再重新记录 FPS、队列欠载和 SRAM/PSRAM。

## GameRender 后续选择

现有 1.2 wire 和逐像素参考保留。只有同 AOT 的分项证明某个准备步骤占优后，
才考虑增加更早的材质/光照提交边界。命令准备、校验和复制均计入整帧成本。
候选继续复用 Guest 已拥有的输出/深度/材质存储，拒绝时可原子回退。
新边界必须在上游当前原函数差分和实际场景中证明质量与收益，再改公开默认值。
