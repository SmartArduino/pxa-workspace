# PXA 固定目录与 SD 系统盘设计

状态：2026-10-18 设计契约；**整应用安装、私有镜像后端及无 Flash 文件分区启动尚未实现**。已实现的固定应用媒体根与可选授权只读访问是独立的先行能力。本文补充并修订[多卷设计](pxa-multi-volume-design.zh-CN.md)的安装布局、控制存储位置及启动规则；对应[机器可读布局草案](design/pxa-storage-layout.draft.json)。

## 1. 固定规则

每个受管理卷使用相同的卷内根目录 `/PXA`。安装使用系统默认卷或用户在系统设置中指定的卷，系统决定卷内目录；安装器、Files、Store 和 PXADB 共用此规则，不提供任意安装路径输入框。**默认安装和游戏启动不弹目录选择器。**

用户操作只涉及“安装”“启动”和可选的“移动到 SD 卡”，不涉及文件夹。单 SD 槽、没有内部文件分区的设备直接使用板策略指定的 SD 卷；初始化系统盘时也固定创建 `/PXA/system`，不询问字体或系统目录。多存储设备的设置最多显示“内部存储 / SD 卡 / USB 存储”等卷选项，默认安装仍直接沿用系统策略。缺卡或空间不足时显示插卡、释放空间或更换存储设备的操作，不能退回要求用户寻找目录。

| 固定目录 | 内容 | 谁管理 |
| --- | --- | --- |
| `/PXA/system` | 系统控制记录、系统资源代际、字体与主题 | Host 系统管理器 |
| `/PXA/app` | 已安装应用的签名清单、AOT/Wasm 及包内资源 | 包安装器；激活后只读 |
| `/PXA/data` | 每个应用的私有文件、Storage KV、缓存及临时数据 | Host 私有存储服务 |
| `/PXA/media` | 按应用身份自动绑定的游戏资源；用户共享文件 | Host 创建应用专属子树；访问其他目录才需授权 |
| `/PXA/.pxa-control` | 卷登记副本、候选代际、传输暂存及回收记录 | Host；不能产生激活权限 |

这是借鉴 Android 的应用专属目录及共享目录划分，而不是复制其实现或权限规则。Android 的官方文档也将应用专属持久文件、缓存和共享文件分开，并要求处理外部介质不可用的情况：[Android 应用专属文件](https://developer.android.com/training/data-storage/app-specific)。

这里的 `/` 指**所选卷的根**。例如 Host 原生挂载点为 `/pxa/sdcard` 时，卡上 `/PXA/app` 对应 `/pxa/sdcard/PXA/app`；挂载点不是 Guest ABI。第二张卡、USB 分区和内部文件卷都沿用相同目录，使用 VolumeId 区分，不能用“第一张卡”的顺序决定安装身份。

游戏默认把可导入大资源放在 `/PXA/media/<app-key>`，由安装器/导入工具按身份定位，SDK 自动打开；不得把“请用户选择游戏目录”作为每个游戏的必经步骤。已打入签名包的资源仍在 `/PXA/app` 中，经 Assets 自动访问。已有 `/roms`、`/PXA-games` 等用户目录继续可用，用户主动导入时才走可选授权流程；不自动移动或删除用户原有文件。只有系统卷需要创建 `system`，只有安装或产生数据时才创建相应子树。

## 2. 两种硬件配置使用同一架构

控制存储由 `SystemRoot` 解析，**不要求存在 Flash 文件存储分区**。启动固件、恢复能力和可更新的系统数据分开配置。

| 配置 | Flash 中 | 系统卷与应用位置 |
| --- | --- | --- |
| `internal-system` | 启动固件；可选的内部文件系统 | 内部卷的 `/PXA/system` 为控制存储；应用可以整体放在内部或 SD |
| `removable-system` | 启动固件及其内置恢复资源；无需 LittleFS/FAT 数据分区 | 选定 SD 的 `/PXA/system` 为控制存储；字体、应用和私有数据均可在该卡 |

NVS、OTA、校准等板级分区是否存在由板定义，不作为 PXA 应用安装或系统文件存储的前提。实现不能为了初始化 PXA 而强制打开、格式化一个不存在的 `storage` 分区；有 NVS 的板也不能把应用数据偷偷回退到其中。

`SystemRoot` 包含 `VolumeId + mount_epoch + SystemId + control_backend`。位置登记、owner、目录授权和事务均通过它访问，不能再拼接 `CONFIG_PXA_MOUNT_POINT/CONFIG_PXA_STATE_ROOT` 来推断控制卷。`SystemId` 是创建系统实例时生成的非零随机 128 位 ID；更换系统盘意味着换一个系统实例，不能把原实例的授权带给新卡。首版每个系统卷只承载一个 SystemId，已有其他系统时须选择导入/恢复，不能覆盖初始化。

内部保存少量记录是第一种配置的选择，**不是第二种配置的要求**。设备硬件密钥或已有安全存储可作为可选保护能力；本设计不要求新增 eFuse 写入，也不以此作为普通 SD 系统盘的启动条件。

## 3. SD 系统盘的启动与恢复

启动顺序固定为：

1. 初始化显示、输入、块设备及固件内置的最小恢复界面；此时不读外部字体，也不启动 Guest。
2. 根据板级启动介质策略枚举候选卷。固定单 SD 槽可指定端口与分区；多候选且不能唯一确定时，由恢复界面选择。不得以卷标、扫描顺序或“最新修改时间”选中系统。
3. 检查布局版本和控制后端，挂载所选系统的控制存储，先恢复中断事务，再解析应用及系统资源的激活登记。
4. 通过已登记的系统资源代际加载字体、主题等，建立完整桌面，然后允许启动应用。

新卡由明确的“初始化 PXA 系统盘”操作创建目录和控制镜像，不重分区或格式化用户整张卡。已有 `/PXA` 文件、未知布局版本或无法恢复的控制镜像应提示冲突/修复，不能覆盖后当空卡启动。

固件内必须带最小 ASCII 字体、必要图标及错误码显示，或等价的有界恢复字库。这些是固件资源，不要求 Flash 文件分区，也不需要把整套中文字体常驻 RAM。完整字体缺失时显示恢复界面；单个非必需主题缺失则用内置样式。

系统卷丢失时停止全部依赖该系统的 Guest、安装任务、授权与字体读取；切换到独立的固件恢复界面，不能继续使用 FreeType 中仍可能回调 SD 的字体对象。后端正在执行的 I/O 先进入取消/失效状态，物理调用结束后才能销毁上下文；驱动无法有界退出时由看门狗复位进入恢复。检测来自驱动事件或 I/O 失败，只有具备相应驱动能力的板才发布热插拔支持。首版只允许重启后重新选择系统盘，不做运行中热换系统。

无 Flash 持久状态时，不能声称系统会记住“上次信任的是哪张卡”。板策略可固定设备/分区，用户可明确选择系统，但介质身份与旧状态的自动认证需要额外的可靠信任锚。新卡上的包仍须经过安装/导入校验才能加入其系统登记；插入普通存储卡不自动运行其中的程序。

## 4. 卷内应用隔离布局

```text
<volume>/PXA/
  system/                         # 仅系统卷必需
    control.lfs                   # 可恢复的权威控制存储
    resources/<resource-id>/      # 不可变系统资源代际
      fonts/...
      themes/...
  app/<app-key>/<store-id>/<release-id>/
    ...                          # 原始签名包布局；代码及包内资源
  data/<app-key>/<store-id>/<data-id>/
    private.lfs                  # 持久私有文件及 KV
    disposable.lfs               # 缓存及临时文件，首次使用才创建
  media/<app-key>/duke3d.grp      # 自动绑定资源根，启动无需选择目录
  .pxa-control/
    stores/<store-id>/...
    staging/<operation-id>/...
```

`app-key` 为小写 64 字符 SHA-256 十六进制：输入是 ASCII `PXA-APPKEY-1`、32 字节 lineage root key ID、u16 小端 App ID 字节长度、原始 App ID 字节。不可只用显示名称或 App ID，以免不同发布者占用同一数据目录。签名密钥按既有 lineage 规则轮换不改变此键；登记的完整身份仍为最终校验依据。

`store-id` 是系统在该卷创建的随机 128 位命名空间，并绑定 SystemId 与 VolumeId，避免不同设备/系统各自在同一张卡上的管理记录互相回收。`release-id`、`data-id`、`operation-id` 也是不复用的随机 128 位 ID，磁盘上均为 32 字符小写十六进制。ID 冲突时重生成或拒绝，不能覆盖已有目录。目录说明副本可提供应用名供管理工具显示，但不提供 owner、授权或激活证明。

Files 显示“Duke Nukem 3D / 应用 / 数据 / 缓存”等可读名称；哈希目录是 Host 的物理映射，不是让用户或开发者手动输入的路径。包自身相对路径保持签名清单原样，安装计划须检查加上固定前缀后的原生路径总长，不能只检查包内路径。

每个身份只在当前 SystemRoot 中有一个激活登记。release 与 data 分别标识，因此更新代码不更换存档，清除数据则创建新 DataId；等待旧引用归零后才回收旧树。外部目录扫描只能发现可导入内容及孤儿对象，不能决定激活状态。

## 5. “整个装到 SD”的明确含义

新安装选择位置时默认使用 `whole-app`：代码、包内资源、私有文件、Storage KV、缓存、临时文件及自动绑定的应用媒体根全部在目标卷；不保留隐式的内部私有数据副本。界面显示“安装到：SD 卡（应用和数据）”，并给出包大小、数据预留、外部导入资源及更新所需临时空间。

`SystemRoot` 可以在同一卡，也可以在另一合格卷。系统控制记录、系统级授权与设备安全能力由系统管理，不能因单个应用迁移而移动；它们不属于该应用的存档或私有 KV。在 `removable-system` 配置下，这些控制记录本身也在 SD。

兼容模式包括 `legacy-fixed`（现有内部状态根）及明确选择的 `package-only`（只移动包，保留数据）。两者不得冒充“整个应用在 SD”。已有资源目录授权也不是安装位置：包、私有区和用户授权的共享 ROM 可以位于不同卷，用户资源不会被安装器默认复制或卸载。

旧 FS 1–8 的逻辑私有根、Storage KV 和 Assets 的包相对路径保持原样。根目录解析由启动时的单一 PlacementSnapshot 完成，FS 与 KV 不能各自查一次可能正在改变的位置。`fs.app_media()` 通过 OPEN_ROOT kind 5 和 `app-media-root` feature 自动取得本应用媒体根，Permission 与 GrantId 均为零；Host 根据身份及安装策略授权，不能接受 Guest 任意填写挂载路径。普通 Guest 不取得 `/PXA` 原生路径，也不用申请“读整张 SD”才能访问自己的数据。

目标卷不可用时拒绝启动，并显示缺失的卷或系统盘；不能创建空的内部数据目录继续运行，避免两套存档分叉。只读系统盘可进入恢复/诊断；首版不在无法提交授权、数据或恢复记录的情况下正常启动可写系统。

## 6. FAT 上的私有数据后端

私有 FS 的字节精确、大小写区分及原子替换契约不能直接映射到 FAT 文件名。因此普通 FAT 卡上采用 **LittleFS2 私有镜像**作为候选兼容后端，尚需实现和故障注入验收；不伪造 FAT 的 POSIX 能力。

| 镜像内逻辑目录 | 服务可见范围 |
| --- | --- |
| `private.lfs:/files` | 旧私有 FS 根及新的 private root |
| `private.lfs:/kv` | Storage KV 后端；不能经 Guest FS 访问 |
| `disposable.lfs:/cache` | 有配额的可重建缓存 |
| `disposable.lfs:/temporary` | 临时数据；应用实例退出后可清理 |

镜像通过直接 LittleFS API 接入服务后端，或通过经过验证的 VFS 接口接入；不把现有仅适用于内部 LittleFS 的 fd 私有扩展冒充 FAT API。包与大型 PAK/GRP 直接从外层卷读取，避免为只读大资源增加一层私有镜像。

控制存储同样需要可恢复语义。在 FAT 系统卷上，`control.lfs` 使用同类镜像后端；在具备合格原生语义的内部卷上可以使用等价原生后端。控制后端必须先可用，安装位置登记才有提交点。“内部提交”在多卷设计中应理解为**权威控制存储提交**，不再限定物理 Flash。

镜像本身不提供加密；Host 能隔离 Guest，不能据此声称电脑无法读取或修改 SD。LittleFS 的内部恢复也不能消除外层 FAT 元数据损坏、控制器断电丢写或介质整体故障。驱动的同步、重挂载及掉电矩阵通过前，不能发布 `whole-app` 或 `system-store` 能力；FAT 可写不等于这些能力成立。

## 7. 有界内存、容量与增长

镜像不能一次读进 RAM。首版建议 4096 B 逻辑块、512 B 读/写粒度、512 B LittleFS 缓存、128 B lookahead；每个活动持久镜像的基础缓存为 1152 B，每个打开文件再加 512 B，另计结构体、fd、共享 I/O 缓冲、外层 FatFS 与任务栈。数值是待测配置，不能将基础缓存称为存储系统总开销。

只挂载正在使用的应用数据镜像，控制镜像单独保持活动；每个系统允许的同时活动镜像和文件数由有界预算决定。按物理设备共用 I/O 调度，不为每个镜像新增线程。安装流式写入，游戏读取使用少量共享页；SD 容量增加不扩大 Guest 线性内存，也不提供 SD XIP。

容量盘点与实时性能采样分开：帧率、内存和队列状态只读有界内存快照，不能顺带遍历文件系统。需要遍历的容量统计通过独立后台任务更新缓存，并附采样时间；GUI 刷新和 Guest 回调不直接触发全盘扫描。安装准入仍由预留管理器重新核对可用空间，不能仅信过期显示值。本次 PXADB 新增的 `PERF FPS` 已遵守不扫描存储的规则；完整多卷容量调度仍属后续实现。

计划分别记录逻辑数据配额、镜像物理容量及文件系统保留空间，不能把三者混为一谈。新数据镜像以小容量创建，首轮候选为 256 KiB 起、按 256 KiB 增长；实际最小值须通过格式化/更新压力测试。创建及增长均先计入卷预留；不为每个已安装但从未启动的应用预分配大镜像。安装时向用户明确数据初始空间和后续最大额度；后续增长仍可能因卷被占满而失败。

增长发生在应用停止或数据根已静止时：

1. 预留并实际分配外层文件新增区间，写入擦除态并同步外层长度和分配元数据；不能仅 seek 产生未分配洞。
2. 验证 backing file 长度和边界，调用 LittleFS 的 `lfs_fs_grow`，同步并卸载、重新挂载确认新的 superblock 容量。
3. 记录结果。恢复时允许 backing file 比 superblock 大，尚未使用的尾部作为未提交预留；禁止 superblock 容量超过实际可访问文件长度。

挂载时 `block_count=0` 从盘上读取实际容量，块回调仍以验证过的 backing file 长度进行整数溢出和越界检查。本仓库 LittleFS 已有此配置及 `lfs_fs_grow`，但相关镜像适配尚未实现。增长报错后重新挂载恢复，不能信任该失败调用留下的内存容量值。此机制不承诺外层 FAT 受损时仍可恢复。

首版不在线缩容。回收镜像空闲容量通过停止应用、复制有效数据到新镜像、验证并提交新 DataId；缓存镜像可以在无引用时整体回收，持久镜像不能因满盘自动删除。单镜像大小还受 FAT 单文件限制、LittleFS 块地址范围及实现整数上限共同限制，u64 协议不意味着后端无限大。

## 8. 安装、更新、整应用移动与卸载

安装计划把 `layout_version + placement_policy + package_target + data_target + app_media_target + control_store + expected_location_revision` 固定下来，同时预留代码、数据、资源复制、系统提交和旧新代际重叠空间。`whole-app` 要求 package/data/cache/temp/app-media 在同一目标卷，能力缺失时明确拒绝。用户主动授权的其他共享目录保持独立。

新包写到目标卷唯一候选代际，执行现有安装时签名与完整内容校验；建立新数据镜像并同步，然后在权威控制存储一次提交整条 Placement。提交前失败只留下待回收候选，提交后取消只能停止清理。继续遵守现有策略：启动/运行不新增完整内容哈希扫描；结构检查不被宣传为防离线篡改。

应用更新创建新 ReleaseId，沿用 DataId。系统字体/主题更新也使用独立不可变资源代际，先验证候选、提交控制登记，再于重启或释放全部字体引用后切换；不覆盖 FreeType 正在读取的文件。系统资源代际与固件资源 ABI 兼容后才能激活；不兼容时保留恢复界面。

“移动到另一卷”默认整体移动：准备代码及本应用固定媒体根的副本后停止应用、排空数据写入，复制并验证持久数据；缓存可丢弃重建，临时文件不迁移。一次控制事务提交代码、数据和固定媒体根的新位置，不能先切代码再切存档。旧镜像和包保留到提交完成且全部引用归零后再回收。固定媒体根中的用户资源复制完成后，原副本默认保留，并在完成页明确可回收空间；系统只按明确的所有权记录或用户清理操作删除，不能误删其他系统复用的媒体。用户主动授权的其他共享目录只报告原位置，不随应用默认复制。

迁移系统盘是独立维护操作：停止所有 Guest 与写入者，明确复制控制存储及所选系统/应用内容，以新的启动介质选择完成切换。无内部持久引导选择的设备无法声称跨两张可移除卡原子更新启动偏好；首版要求用户在恢复界面选定目标盘或更换固定槽中的卡并重启，原盘保留为可恢复副本。复制的系统实例不得同时作为两份独立可写状态运行。

卸载默认删除该应用管理的代码、私有数据和缓存，可显式选择保留存档；不删除 `/PXA/media` 或用户授权目录。离线卸载写入精确绑定 SystemId、StoreId、VolumeId、AppKey、ReleaseId/DataId 的 tombstone；介质回来后只回收这些对象。另一系统的同名应用、手工复制的目录或新 DataId 不在清理范围内。

## 9. 保护固定目录

隐藏目录名不是权限。Host 的目录解析器、可信选择器、Files 和 PXADB 普通文件命令都须保护以下位置及其所有后代：`/PXA/system`、`/PXA/app`、`/PXA/data`、`/PXA/.pxa-control`。

保护以**卷根位置**及原生名称等价规则判断，包括大小写与别名；不能只看相对于 Grant 的字符串。例如授权卷根后仍可访问 `PXA/media`，但不能进入 `PXA/data`；授权更深的用户目录后，其中名为 `data` 的普通子目录不因此被禁止。受管理树内不能成为授权根。FAT 8.3 别名须由后端可靠解析或拒绝，不能让 `~1` 绕过保护。

Host 安装/维护接口使用专门 capability 与有期限上传租约进入受管理树，普通调试传输不能成为后门。迁移部署保护规则应先于在 `/PXA/app` 写入任何安装内容。现有先行只读 SD 后端主要保护 `.pxa-*` 名字，**尚不满足此新布局的完整保护要求**。

## 10. 必须通过的验收

- 构建并启动**完全没有 Flash 文件分区**的板配置：固件仍能显示无卡恢复页；初始化合格 SD 后加载其字体、桌面和应用，重启后恢复设置与存档。
- 系统卷与应用卷分别在 SD 的不同分区、两张卡或内部/外部组合；每卷统一目录，无扫描顺序依赖；缺任一必需卷时不产生空存档。
- 持久文件 `A` 与 `a`、旧 FS 原子替换、KV 隔离、Quota、取消及退出行为不随物理位置改变；镜像损坏绝不自动格式化。
- 在镜像分配、增长、候选写入、控制提交、整应用移动、资源切换及回收各阶段注入 I/O 错误和复位；验证旧或新登记可恢复，绝不部分切换。
- 根目录授权、大小写变化、短名别名、普通 PXADB push/rm 均不能读写受管理树；共享媒体正常授权、卸载后保留。
- 测量镜像与外层 FAT 的实际 RAM 峰值、冷启动、字体读取、存档写入 p95/p99、呈现 FPS 和音频欠载；按结果决定是否开放相应后端能力。

## 11. 实现边界与代码落点

| 边界 | 下一步改动 |
| --- | --- |
| 板配置、分区表及 `pxa_integration` | 分离挂载系统卷、可选内部文件卷和其他资源卷；先恢复 SystemRoot，再启动 Host；保留内置恢复页 |
| `firmware/main/app_main.cc` | 去除 PXA 对无条件 NVS 初始化的依赖；板级网络/校准后端另行声明必需能力，不能把所有板的需求混在 PXA 文件系统初始化中 |
| SystemRoot / StorageResolver | 提供控制存储、已激活系统资源与 PlacementSnapshot；服务不再自行拼接状态根；以布局版本处理 legacy 导入 |
| 系统偏好与启动器顺序 | 审核现有 NVS 调用，PXA 自身的主题、字体、排序、权限和安装偏好在 removable-system 下统一落到控制存储 |
| 私有 FS、Storage KV 与包加载 | 按同一快照选择后端；私有镜像保留旧语义；只读包不经数据镜像；错误不触发空目录回退 |
| 安装器、Files、Store 与 PXADB | 共用固定布局和保护器；whole-app 计划、一次代码/数据提交、精确 tombstone 与有界回收 |
| 字体/主题加载 | 由 SystemRoot 解析已激活资源代际，持有租约，切换前释放全部读取者；禁止硬编码内部字体路径 |

实现顺序为：固定布局解析及保护 → 镜像块后端与故障测试 → SystemRoot 引导及无文件分区板配置 → whole-app 安装/迁移与管理界面 → 逐板真机验收。兼容旧内部布局的启动不主动移动数据，转换为新布局须经过正常迁移事务。

当前固件仍使用内部 `pxa-state` 和内部系统字体路径，入口仍调用 NVS 初始化。GameKit 的固定应用媒体根已实现，并通过首次启动及重启后的无选择器读取验证；完整固定安装布局及两种 SystemRoot 配置仍是下一步实现契约。
