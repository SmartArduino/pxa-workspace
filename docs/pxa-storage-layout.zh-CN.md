# PXA 固定目录与整应用安装

PXA 在每个受管理卷内使用 `/PXA`。用户选择的是“内部存储”“SD 卡”等存储卷，系统管理卷内目录；安装及启动不要求浏览文件夹。Host 原生挂载点可以改变，安装身份不依赖 `/pxa/sdcard` 等路径。

本文描述卷内应用布局、签名资源代际与原生迁移协议。系统资源热切换及旧布局转换仍有接入边界。卷注册与应用访问接口见[多卷存储接口](pxa-multi-volume-design.zh-CN.md)，机器可读摘要见[布局草案](design/pxa-storage-layout.draft.json)。

## 固定布局

```text
<volume>/PXA/
  volume.0.pxv                    # 本卷 UUID 镜像
  volume.1.pxv
  apps/<publisher-directory>/<app-id>/
    install.0.pxi                 # 本地认证安装记录
    install.1.pxi
    package/                      # 当前签名清单、代码与包内资源
    ...                           # 安装器管理的代码事务槽
    data/<data-generation>/
      private.lfs                 # FAT 上的私有 LittleFS 镜像
      ...                         # 原生私有文件系统使用目录后端
  cache/store/
    .store-<token>.pxa             # 下载暂存或完成的离线包
    .store-<token>.pxa.meta        # 离线包的认证完成描述
  media/<publisher-directory>/<app-id>/ # 当前手工导入的游戏资源
  system/fonts/                   # 板策略选定卷上的系统字体
```

`publisher-directory` 优先使用签名包作者资料中的开发者名称，例如 `lucinhu`；名称已被占用时追加签名根指纹，例如 `lucinhu-17982acd`，发生指纹前缀冲突时继续延长。无已验证作者资料的包继续使用完整签名根目录。App ID 来自签名清单。名称只用于磁盘路径，应用跳转和安装记录继续使用完整 `publisher-root + App ID`，不因昵称、显示语言或挂载位置改变。

每个卷的 `apps` 和 `media` 发布者目录分别包含 `.publisher.pxi`，由设备认证绑定卷身份、用途、完整签名根与实际目录名；新安装不依赖逐应用 NVS 表。首次分配的名称保持稳定，修改作者昵称不会移动已有应用。无法验证的目录不被接管，同名作者不共用数据。

旧完整签名根目录先提交认证名称，再原子改名；中断后旧目录或新目录均可恢复，发现双重归属时拒绝模糊访问。应用目录只有在同作者应用空闲且没有待恢复搬家事务时才迁移；已存在的共享媒体目录只在启动阶段迁移，避免影响其他应用已打开的目录授权。运行时安装可先保留媒体旧路径，下一次启动完成改名。既有目录授权在访问时按已认证的名称解析，授权 ID 和权限保持不变。

`data-generation` 使用固定宽度十六进制编码。更新保留当前数据代际；清除数据准备新代际、提交本地记录后再回收旧目录。历史数据代际零使用 `home/private` 兼容路径。Guest 只访问 Host 提供的私有 FS、KV 和 Assets，不能拼接这些原生路径。

`private.lfs` 是磁盘文件，并非同等大小的常驻 RAM。Host 为 FAT 上的私有文件、KV 与权限提供一致的文件名和原子替换语义；只有满足相同语义的原生文件系统才直接使用目录。LittleFS 必须关闭 `LITTLEFS_SPIFFS_COMPAT`，避免删除文件时顺带删除空父目录。

## 权威记录与空间

安装记录位于应用所在卷，包含应用/资源卷身份、InstallID、签名清单摘要、代码及数据代际、启用/归档状态，并使用设备密钥认证。发现目录或校验 CRC 不产生执行权限；启动前仍重新验证签名及代码。多个卷出现相同应用身份时拒绝模糊的第一匹配，不自动覆盖存档。

新安装不写内部 Flash 的逐应用定位表或下载登记表。设备密钥等少量平台安全状态与逐应用记录是独立的：当前 ESP 实现使用 NVS 中一个固定设备密钥，已有旧版应用保留兼容适配器。旧版定位表不是新安装的前提。

安装计划依据所选文件系统的分配单位计算解包文件、控制记录、初始私有后端、实际下载暂存峰值和保留空间。显示用容量是缓存快照；确认后重新查询容量并原子预留。下载和提交使用同一个预留对象，不能在下载完成后临时要求内部 Flash 再容纳一份。

原文件已位于设备上时只计后续新增峰值，不再次计入已占用的传输副本。下载离线包只预留缓存所需空间；安装离线包时再确认解包与私有数据空间。文件系统最大文件大小和 Host 配置仍可限制单包大小。

## 安装与更新

1. 商店提交票据、完整包大小/摘要和应用身份，不提交原生路径。
2. Host 获取有界签名清单，验证发布者、应用身份、文件清单及权限，生成可安装卷选项。
3. 系统确认框显示应用、版本、发布者和存储位置。单卷设备无需选择目录；多卷设备可切换合格卷。新安装推荐合格内部卷，其次是可移除卷；更新沿用已有卷。
4. 确认后刷新容量并预留选定卷，直接将下载写入该卷的固定缓存目录。
5. 校验完整容器大小、SHA-256、包签名和解包文件，准备私有后端，再提交应用本地记录。确认时的清单摘要及旧记录代际必须仍匹配；不在下载后静默接受另一版本或覆盖并发变化。
6. 提交完成后回收旧代码事务槽。相同版本仍验证来源和已安装代码，但不无故重写安装记录或重新创建私有数据。

后端优先通过 `install-metadata` 返回清单前缀；旧后端可通过容器下载接口的有界前缀读取兼容。预检不替代完整安装验证。

系统文件管理器点击 `.pxa` 时，复用 Host 原生确认框选择存储卷。校验及安装在已有运行时任务上执行，界面显示检查和安装进度；文件管理器只提交任务，不在 LVGL 任务栈内解包。确认期间保留输入文件所在卷的挂载实例，提交仍检查原实例及已批准的签名清单摘要；输入被替换、卷不可用或应用记录已变化时拒绝使用旧结果。取消和失败释放引用与预留，并保留用户的输入文件。

本地资源包可单独安装到选定卷的固定媒体目录，不产生应用安装条目。资源包优先推荐输入文件所在的合格卷；引用资源的本地应用包要求对应签名资源代际已安装，然后独立选择应用卷并复用资源。此入口同样不需要内部 Flash 的逐应用记录。商店能够在同一安装事务中先取得资源，再提交应用，无需用户手动分步导入。

完成的离线包与其归属描述保存在同一卷。重启时从已挂载卷发现，无需内部全局索引。缓存描述认证绑定卷、调用者、应用和容器摘要；换卷重放及篡改不能获得归属。拒绝或失败的离线安装保留缓存以供重试，成功后消费它。未写入完成描述的中断传输可清理；设备密钥暂不可用时不把未知完整缓存当作垃圾删除。

## 存档、授权与卸载

私有 FS、KV、权限及持久目录授权共享同一个已验证安装会话，跟随应用所在卷。权限记录绑定卷、InstallID、发布者、App ID 和数据代际，不通过另一应用的同名目录获得授权。

归档先提交并镜像本地记录，再删除代码，保留 InstallID、数据及授权；重装归档应用继续使用这些数据。冷启动时，缺少包内显示资料的归档项使用稳定 App ID，重装后恢复包内本地化名称。完整卸载删除整个应用 home。清除数据切换数据代际，旧授权不随新数据恢复。手工导入的 `/PXA/media` 不由这些操作隐式删除。

跨卷移动由 Host 显式发起，保留 InstallID、数据代际、签名代码摘要和资源绑定，安装记录从 N 递增至 N+1。目标 home 的双份 `.transfer.{0,1}.pxm` 记录存在期间，该安装不参与发现、启动或普通维护；损坏记录也不会被当成空安装。

Host 先复制并逐文件回读校验私有数据，再验证和重新签封权限、目录授权。源卷的转移凭据位于受保护的 `PXA/apps/.transfers/<transfer-id>/`。目标准备完成后，源 home 同卷改名到其中的 `source`，同步目录，并在目标卷持久保存设备签封的交接凭据，之后才提交目标记录。仅凭源卷离线不能推断交接成功；已有有效交接凭据时，可以在源卷离线后继续提交已准备的目标安装。

提交前失败的重试重新复制源端当前数据，避免把旧快照与新存档合并；交接之后使用已准备的私有文件系统，缺失或损坏时拒绝继续，不重新格式化。只有双份目标安装记录提交完成，才解除目标隔离并回收旧源。转移记录和数据均保存在参与卷内，没有内部 Flash 的逐应用登记表。

启动时，Host 在处理应用启动队列之前扫描已挂载卷的目标转移记录，并验证、继续尚未完成的迁移。扫描不把源端隐藏交接目录当作新安装；源卷在交接前缺失、凭据损坏或空间不足时，保留隔离状态等待后续恢复。恢复复用已有运行时任务和有界 PSRAM 工作区，不新增常驻任务栈。开发连接的旧会话清理采用非阻塞锁尝试，恢复期间仍可连接并读取日志；旧会话尚未清理时，拒绝新的传输写入，避免延迟清理误删新文件。

在“设置 → 应用 → 应用详情”中，未运行的新布局应用可选择“移动应用与数据”。Host 原生确认框显示当前卷、可用目标及空间需求，并说明资源保留在哪个卷；只选择存储设备，不选择目录。预览不创建目标目录、迁移凭据或空间预留，取消不改变安装。确认后重新检查卷实例、容量及完整源安装记录，安装被更新、清除数据或重新安装时拒绝使用旧确认结果。

迁移由系统持有，复用已有运行时任务，在复制期间显示原生进度遮罩，完成后刷新应用列表；不依赖商店进程或增加常驻任务栈。开发入口仍提供继续迁移功能。“移动应用与数据”保留原有资源卷绑定；未绑定的手工媒体目录会使该迁移被拒绝，避免代码移动后改变媒体查找位置。归档应用提供“移动归档数据”，使用同一认证交接与恢复协议迁移私有文件、KV、权限及本地安装记录；保留归档标志，不要求代码目录存在，也不创建虚构的清单或可执行包。容量计划只计私有后端及交接记录，资源保留原卷绑定；恢复启动仍需独立验证重新安装的签名代码与资源。旧版更新兼容路径不代表已转换为新 home。

旧布局应用在详情中提供“升级存储布局”。这一步在当前原生私有卷内收拢代码、私有文件和 KV，资源保留在原来的实际卷。预览完整校验签名代码、权限及目录授权，不创建目标或登记行；确认后先保存设备认证的恢复日志，再退役旧代码、原地改名私有目录，并为新的 InstallID、卷及数据代际重新认证权限和目录授权。手工媒体别名在原资源卷内改名为固定的发布者/App 目录，不复制大资源。已确认存在的原存档在恢复时缺失、目标目录冲突或资源卷不可用，均会阻止提交，不以空目录替代它们。

旧布局升级使用明确的日志种类，与普通跨卷移动分开恢复；新的双份认证安装记录发布后，旧准备阶段日志的重放不能重置已生效的权限。旧权限文件、目录授权和已核对所有者的兼容记录在新记录持久化后尝试回收，Flash/NVS 清理失败不阻止新安装运行。旧定位行只在原代码和私有路径均不存在时回收，仍有旧存档的定位信息保留供恢复。未含发布者资料的已安装旧包可继续使用固定的旧私有目录和发布者/App 媒体路径，不为启动分配新的 NVS 行。旧 AppKey 散列媒体目录仅由明确的升级入口识别和收拢，运行时不生成这套旧路径。升级成功后，可再通过“移动应用与数据”选择其他卷。

已绑定签名资源的应用还提供独立的“移动游戏资源”。确认后直接从原资源代际复制到目标卷，或完整校验并复用目标已有的同一代际，再比较确认时的完整安装记录并提交新的资源卷绑定。代码、InstallID、私有数据代际和权限不变，只递增安装记录代际；应用卷仅预留本地记录更新空间，不重复暂存代码或私有镜像。确认前后的介质挂载实例必须一致。复制或校验失败时，原记录与原资源继续有效；断电产生的已准备资源可供重试复用。旧资源副本暂时保留，待具备离线卷引用识别的回收策略后清理，当前位置变更尚不保证释放原卷空间。

底层安装记录也可显式绑定手工导入的媒体：设置 `HAS_MEDIA`，不设置 `MANAGED_MEDIA`，媒体摘要为零，目录固定为资源卷的 `/PXA/media/<publisher-root>/<app-id>`。这表示设备认证的卷与目录绑定，不表示资源文件具有发布者签名。启动会逐级检查目录并保留该卷的挂载；目录丢失或被符号链接替代时拒绝访问，不创建空目录。应用跨卷移动保留此绑定，不复制或改写媒体；没有签名资源声明的后续代码更新同样保留它。签名资源安装接口拒绝将手工目录作为签名代际处理。旧别名目录的收拢、旧权限转换及恢复日志仍由旧布局迁移入口负责，现存旧应用尚不会被自动转换。

## 硬件拓扑与启动

| 存储配置 | PXA 行为 |
| --- | --- |
| 单个 Flash、一个文件系统 | 注册一个卷，使用同一固定布局 |
| 单个 Flash、多个文件分区 | 板驱动分别挂载并注册，每个分区有独立卷身份与容量 |
| 多个 Flash | 每个已挂载文件系统注册为独立卷；共享物理设备不等于共享卷身份 |
| Flash 文件卷加 SD | 两卷都可承载完整应用；缓存及私有数据跟随所选卷 |
| 没有 Flash 文件分区，只有 SD 或另一 Flash 文件卷 | 主文件分区可禁用；先注册外部卷，再发现应用及加载系统资源 |

这些是通用 Host 注册模型；具体板是否支持多分区、额外 Flash 或热插拔取决于其驱动，ABI 不会自动产生硬件支持。

GameKit 没有内部文件分区时可将 SD 挂到 `/pxa`；有内部卷时 SD 可挂到 `/pxa/sdcard`。同卡上的卷身份和安装记录不因路径变化而改变。主分区缺失或挂载失败不能触发格式化，也不能阻止板继续注册外部存储。

字体固定从板策略选定卷的 `/PXA/system/fonts` 读取，完整字体缺失时使用固件可用的基本资源。当前 GameKit 的介质挂载在启动时完成，插卡后需重启；运行时系统字体切换、系统卷丢失的恢复界面及完整热插拔生命周期尚未接入，不能直接拔除仍有字体/应用引用的介质。

## 游戏媒体与签名资源包

现有游戏使用自动绑定的只读 app-media 根访问 `/PXA/media/<publisher-directory>/<app-id>`，无需每次选择游戏文件夹。选择其他用户目录时才使用目录授权接口。

Manifest 0.8 区分应用包和资源包。资源包有签名文件清单，没有可执行组件或权限；应用的签名清单直接绑定资源清单 SHA-256，与传输压缩方式无关。准备完成的资源固定存放于资源卷的 `/PXA/media/<publisher-directory>/<app-id>/<resource-manifest-sha256>/package/`。代码更新可以复用同一资源代际，不能原地改写它。

Host 原生安装器可在选定卷准备资源包，并将已准备的准确代际写入应用的本地认证安装记录。安装及启动检查签名身份、绑定摘要与资源文件；运行会话保留精确资源挂载。资源卷缺失或损坏时拒绝启动，不创建空代际掩盖问题。开发工具可用相同 `PACKAGE install-volume` 命令安装签名资源包，再安装引用它的应用。手工媒体目录仍用于旧版游戏，不会被资源安装隐式认领或删除。

服务端先接收签名资源，再接收绑定该资源摘要的代码包；两者随同一版本审核，并通过已审核代码制品的下载凭证交付。Store Installer 0.8 预取两份签名元数据，在 Host 原生确认框选择应用卷和资源卷，联合预留空间，先验证资源代际再提交应用。资源不变的代码更新可复用已完整校验的代际。旧 Host 使用旧版 Profile，不接收 Manifest 0.8。资源组合包的仅下载缓存仍未提供，能力查询不会宣告该功能。
