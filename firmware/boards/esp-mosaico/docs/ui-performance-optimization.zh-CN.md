# ESP-Mosaico UI 刷新优化记录

日期：2026-10-15。板级代码基线：`c3dd9e5`。本轮只修改 ESP-Mosaico，
保留工作区已有的 Watcher、SDK 和其他模块改动。没有烧录设备；下述传输模型、
桌面测试和构建结果不能当作 ESP32-S31 的实测 FPS 或触摸延迟。

本文保留 UI 优化阶段的数据；后续板级接口补齐及其构建内存变化见
[PXA 接入核对](pxa-integration-audit.zh-CN.md)。同一固件输出路径会被后续构建更新。

## 为什么分辨率相近，体验仍可能不同

- Mosaico 是 480×480，Watcher 是 412×412，实际像素数相差 **35.7%**。
  Mosaico 的高 DPI 系统 UI 还有自己的字号、图标和布局，场景负载并不相同。
- Mosaico 虽然在 sdkconfig 中设置了 16 ms，板级代码又把该显示器的 LVGL
  刷新周期改成了 **33 ms**。Watcher 没有这个额外的 33 ms 限制。
- Mosaico 的 CO5300 使用四线 48 MHz QSPI。480×480 RGB565 一整帧为
  460,800 字节，理想纯数据传输就需要 **19.2 ms**，还没有计入 TE、复制和命令。
  这个时钟原本已经是 48 MHz，本轮没有提高。
- 原链路把所有脏矩形合并成整屏宽的行，再复制到 scanout、通过 DMA 发出。
  例如 80×40 的变化会复制和传输 480×40，浪费了六分之五的数据量。

这些是代码中可以确认的差异。缺少相同操作下的两台设备时序数据，不能据此断言
它们各占多少耗时，也不能把所有差异归因于芯片算力。

## 本轮采用的方案

| 修改 | 原因与预期收益 | 内存影响 | 验证 |
| --- | --- | --- | --- |
| 板级 UI 周期 33→16 ms | 让轻量更新更早进入绘制，避免额外的 33 ms 调度限制 | 无额外缓冲、任务或队列 | 固件构建；实际显示 FPS 待测 |
| 两块 LVGL 缓冲从 480 行减至 240 行 | 保留双缓冲，减少工作集和固定占用 | PSRAM 减少 460,800 B | 真实 LVGL 30 帧逐字节对照 |
| 保存脏矩形的 X/Y 边界 | 窄区域快照只复制发生变化的像素 | 边界用 16 位，去掉独立 pending 标志 | ASan/UBSan；重叠、不相交和有行填充的更新 |
| 宽度达到屏幕 75% 时继续整行复制 | 大面积滚动保留一次连续 memcpy，避免逐行调用开销 | 无新增分配 | 桌面复制基准；阈值仍可根据 S31 实测调整 |
| 连续整行合并、DMA 分块使用一次 memcpy | 减少全屏及整行路径的循环与函数调用 | 无新增分配 | 全宽、窄区域、尾块和 DMA 所有权测试 |
| TE 允许时使用窄窗口 | 减少实际总线字节量，保留可靠回退 | 无额外帧缓冲 | 扫描时序模型、对齐与回退测试；物理屏待验证 |

保留已有的一帧背压、异步 flush worker、两个 16 行 SRAM DMA 缓冲和
RAMWR/RAMWRC 连续写入。所有 LVGL 分块合并完毕后才提交一次完整刷新。
生产者可绘制下一帧，但不能覆盖 DMA 使用的 scanout，也不会积累旧滚动帧。
窄区域复制要求两块持久帧在未修改区域保持一致；从游戏直出返回普通 UI 时，
仍先等待前一帧完成，再恢复生产者，之后才合并局部更新。

### 窄窗口与 TE

不能在原先整行扫描跟随的起点直接发送窄窗口：写入变快后会追上扫描光束。
新规划器以 TE 下降沿为活动扫描开始，根据测得的周期和消隐时间选择：

1. 能在当前扫描到达窗口首行之前写完时，优先提前写入。
2. 否则，等当前扫描越过窗口末行，再在下一次扫描到首行前写完。
3. 高度、宽度或时序预算不允许时，继续原来的全宽整行扫描跟随。

仍遵守 X 起点和终点加一为 4 的倍数、Y 起点和终点加一为 2 的倍数。
预算使用两倍理想线速耗时、每个 16 行块 80 µs、额外 2 ms，以及
入场时额外的 1 ms 余量。任务实际唤醒后再次检查剩余窗口，避免错过时机仍启动。
TE 周期未知、超出检查范围或消隐异常时不启用窄窗口；缺少 TE 时保留原有的
有界等待与降频重试，不会每一帧都等待 50 ms。

这些余量是保守的工程估计，**尚未经 Mosaico 真机标定**。若实际紧凑传输
超过扫描截止时间，增加 `scan_overruns`，本次运行自动关闭后续紧凑传输，
直到重启；快照优化仍生效。整行路径原有的 TE/线速假设没有改变。

没有照搬 Watcher 的面板驱动，也没有提高 CO5300 时钟、降低分辨率、关闭抗锯齿
或削弱浮层合成。LVGL 仍保留两个软件绘制单元；在缺少 S31 实测的情况下，
没有把它改成单单元。小型 UI 基元也没有盲目开启 PPA；游戏已有的 PPA 路径保留。

## 可复现的传输量对比

运行：

```sh
bash firmware/boards/esp-mosaico/tests/benchmark_transfer.sh
```

下表由生产代码规划器计算，输入为 TE 周期 16,931 µs、消隐 800 µs。
示例是固定矩形模型，不代表已经采集了真实 UI 的脏区域分布。

| 更新 | 旧快照复制 | 新快照复制 | 旧发送 | 新发送 | 理想数据线耗时（旧→新） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 顶部 80×40 | 38,400 B | 6,400 B | 38,400 B | 6,400 B | 1.600→0.267 ms |
| 底部 80×40 | 38,400 B | 6,400 B | 38,400 B | 6,400 B | 1.600→0.267 ms |
| 开关 96×60 | 57,600 B | 11,520 B | 57,600 B | 11,520 B | 2.400→0.480 ms |
| 滚动 456×352 | 337,920 B | 337,920 B | 337,920 B | 337,920 B | 14.080→14.080 ms |
| 全屏 480×480 | 460,800 B | 460,800 B | 460,800 B | 460,800 B | 19.200→19.200 ms |

顶部和底部的紧凑窗口进入时机不同，传输字节数相同。窄窗口不能保证每种位置
都有相同的端到端延迟。全屏游戏仍交换帧缓冲，原本就不做这次快照 memcpy，
表中“全屏快照复制”对应普通 LVGL UI，不是游戏直出。

脚本也输出本机 `-O3` 复制耗时的 9 次试验中位数，每次 512 次复制。本次记录
80×40 从约 0.77–0.81 µs 降至 0.18 µs，96×60 从 1.26 µs 降至 0.28 µs；
大面积滚动与整屏维持原有连续复制量。它们只是桌面缓存/内存上的结果，
不能换算为 PSRAM 耗时、显示 FPS 或触摸延迟。

## 内存核对

| 板级占用 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 两块 LVGL RGB565 绘制缓冲 | 921,600 B PSRAM | 460,800 B PSRAM |
| 生产者与 scanout 两块持久帧 | 921,600 B PSRAM | 921,600 B PSRAM |
| 两块 16 行 DMA 缓冲 | 30,720 B SRAM | 30,720 B SRAM |
| `g_hardware`（构建 map） | 6,280 B | 6,280 B |

新增紧凑传输计数和回退开关后，利用缩小的区域状态与对象原有对齐，
板级硬件对象大小仍为 `0x1888`。任务数量、预留栈、Guest 线性内存、
游戏帧/深度缓冲和命令队列均未修改；热路径没有新增堆分配。
固定 PSRAM 分配合计减少 **450 KiB**，没有用额外缓存换性能。

本工作区保存的前后构建 map 中，`.dram0.data` 均为 39,172 B、`.dram0.bss`
均为 31,320 B、`.iram0.text` 均为 105,806 B、`.ext_ram.bss` 均为 36,016 B。
Flash text/rodata 分别增加 876/80 B；固件文件增加 960 B。这是工作区构建产物
对比，其他模块已有未提交改动，不应据此归因其他模块的性能变化。

这里只核对了静态占用和明确的缓冲分配。整机运行时稳定占用、首次启动峰值、
图像缓存驻留及任务实际栈水位尚未进行设备测量，不能将这些计算当作真实堆峰值。

## 验证与后续测量

```sh
# 检查内存访问、合成、所有权、对齐、时序、触摸和现有音频恢复逻辑。
bash firmware/boards/esp-mosaico/tests/test_host.sh

# 使用已经构建的 esp-mosaico 模拟器中的真实 LVGL 库。
# 可将另一个兼容模拟器构建目录作为第一个参数传入。
bash firmware/boards/esp-mosaico/tests/test_lvgl.sh

# 激活支持 esp32s31 的 ESP-IDF 环境后构建；不会烧录。
tools/firmware.sh esp-mosaico build
```

本次结果：

- ASan/UBSan 原生测试通过。包含半屏分块、100 次窄/宽且有行填充的更新、
  未修改像素保留、扩宽窗口、游戏交换后返回 UI、DMA 失败所有权，以及
  多种周期/消隐/窗口尺寸下的扫描模型。
- 真实 LVGL 30 帧滚动、圆角和半透明浮层，旧全高与新半高缓冲最终像素
  **逐字节一致**。flush 回调分别为 59/89 次，完整刷新均为 30 次，
  没有把分块回调次数算作 FPS。
- ESP32-S31 固件构建与分区大小检查通过，应用固件为 3,970,288 B，
  剩余应用分区 224,016 B。输出位于
  `build/firmware/esp-mosaico/pxa_esp_platform.bin`。
- 本地原始记录：`local/mosaico-ui-20261015/`，含修改前板级文件、map、
  固件备份，原生日志、LVGL 对照日志、CSV 和 `firmware-final.log`。

本轮没有反复烧录难刷的 Mosaico，也没有得出“实机已经达到某个 FPS”的结论。
下一次正常刷入固件后，应对同一亮度、字体/DPI、页面和滑动手势分别采集：

- `frame_stats` 的显示完成 `fps`、`render_us`、`present_wait_us`、`te_wait_us`、
  `tx_us`，以及独立的输入到显示完成时间。
- `ui_transfer` 的 `compact_total`、`compact_enabled`、`draw_rows=240`。
  `compact_total` 是开机后的 32 位累计计数，会回绕；不是区间 FPS。
- `scan_overruns`、TE 周期/消隐、SPI 错误，以及小区域更新、长列表滚动、
  全屏切换、截图、亮度切换、休眠唤醒和游戏直出/浮层切换的画面。
- 首次启动和重复操作的 SRAM/PSRAM 当前值与本次运行峰值，避免混淆历史最低堆。

完整刷新通常仍受 19.2 ms 数据线耗时及 TE 周期约束，不能通过把刷新定时器
改成 16 ms 就保证 60 FPS。后续优先依据实测决定是否调整窄窗口预算和绘制并行度。
